# 校园乒乓社交与场馆服务平台面试梳理

## 1. 登录与鉴权

这一部分严格按照简历里的这句话来梳理：

基于 Redis 实现手机号验证码登录与 Token 登录态管理，使用拦截器完成用户信息刷新与接口鉴权。

所以只拆成 3 个点：

1. 手机号验证码登录
2. Token 登录态管理
3. 拦截器刷新用户信息与接口鉴权

### 1.1 手机号验证码登录

#### 背景阐述

这个项目面向校园用户，用户更关注的是快速进入系统查看场馆、发布动态、报名活动，而不是走很重的注册流程。

所以我这里没有采用账号密码登录，而是选择了手机号验证码登录，尽量降低使用门槛。

#### 问题剖析

手机号验证码登录本身不复杂，真正需要考虑的是两个点：

1. 验证码必须有时效性，不能长期有效；
2. 验证码校验不能依赖单机存储，否则后续多机部署时状态不好共享。

#### 方案构思

这里其实有两个常见方案：

1. 把验证码存在 Session 里；
2. 把验证码存在 Redis 里。

Session 方案实现简单，但是更适合单机场景，后续如果服务扩容，多机之间的验证码状态共享会比较麻烦。

Redis 方案的优点是：

1. 可以天然支持分布式共享；
2. 设置 TTL 很方便，适合验证码这种短时有效数据；
3. 读取性能也足够高。

所以我最终选择的是 Redis 方案。

#### 复盘总结

所以这一点你可以总结成：

我在项目里采用的是手机号验证码登录。验证码会先存入 Redis 并设置短 TTL，这样既保证了验证码的时效性，也避免了后续多机部署下验证码状态不共享的问题。

#### 高频追问

问题：为什么验证码要放 Redis，不放 Session？

答：因为 Redis 更适合做分布式共享存储，而且设置过期时间也很方便。这样既能控制验证码时效，也能避免多机部署下 Session 不共享的问题。

### 1.2 Token + Redis 登录态管理

#### 背景阐述

验证码校验通过后，还需要解决“用户后续怎么保持登录态”的问题。


#### 问题剖析

这里主要要解决的是登录态如何存储的问题。

常见思路一般有两种：

1. 用 Session 保存登录态；
2. 用 Token + Redis 保存登录态。

#### 方案构思

Session 方案的优点是简单，但是它更偏向单机，后续多实例部署时共享和扩展性都一般。

Token + Redis 方案的优点是：

1. 更适合前后端分离；
2. Redis 可以作为统一的登录态存储中心；
3. 后续做续期、鉴权、分布式部署都更方便。

另外在 Redis 里保存用户信息时，也有两种思路：

1. 存完整用户对象；
2. 存精简后的用户信息。

我最终选择的是只存精简信息，因为鉴权核心其实只需要id信息，没有必要把完整用户对象都放进去，这样会更轻量。

#### 复盘总结

所以这部分本质上是：

我在用户验证码校验通过后，使用随机 Token 管理登录态，并把用户简要信息存入 Redis。这样做比传统 Session 更适合前后端分离和分布式场景。

#### 高频追问

问题 1：为什么不用 Session，而要用 Token + Redis？

答：因为 Session 更偏单机方案，在多实例部署下共享不方便，而 Redis 更适合作为统一登录态存储。另外前后端分离项目本身也更适合 Token 方式。

问题 2：为什么存的是 `UserDTO`，不是完整 `User`？

答：因为鉴权核心其实只依赖 `userId`，同时像昵称、头像这类当前用户的常用基础信息也可以一起放进去，方便后续业务使用。所以我选择存一个轻量的 `UserDTO`，而不是把完整 `User` 对象都放进 Redis，这样既能降低存储成本，也能避免缓存太多无关字段。

### 1.3 拦截器刷新用户信息与接口鉴权

#### 背景阐述

项目里既有游客可访问接口，比如场馆查询、热门动态，也有必须登录后才能访问的接口，比如点赞、关注、发布动态、抢票、签到。

所以这里不能简单把所有接口一刀切拦截，而是既要能识别登录用户，也要允许游客访问部分接口。

#### 问题剖析

那这里的拦截层怎么设计呢？
常见有两种思路：

1. 用一个拦截器同时处理用户信息恢复和登录校验；
2. 拆成两个拦截器，分别处理。

如果把所有逻辑都堆在一个拦截器里，会有两个问题：

1. 游客接口处理起来不够灵活；
2. 用户信息刷新和登录校验耦合在一起，不方便维护。

#### 方案构思

所以我最终采用的是双拦截器方案：

1. 第一个拦截器负责刷新用户信息；
2. 第二个拦截器负责登录校验。

这样拆开的好处是：

1. 游客接口可以正常访问；
2. 如果用户带了有效 Token，系统也能识别出当前用户；
3. 用户信息刷新和登录校验职责清晰，后续更好维护。

另外我会在第一个拦截器里顺手做 Token 续期，因为用户只要处于活跃状态，就应该尽量避免频繁重新登录。

#### 复盘总结

所以这一块你可以总结成：

我把鉴权拆成了两个拦截器，第一个负责恢复用户身份和 Token 续期，第二个负责判断当前接口是否必须登录。这样职责更清晰，也能兼顾游客接口和登录接口。

#### 高频追问

问题 1：为什么要拆成两个拦截器？

答：因为一个拦截器负责恢复用户身份和续期，另一个拦截器负责登录校验，职责更清晰，也更方便处理游客接口和必须登录接口共存的场景。

问题 2：为什么查不到 Token 对应用户时，第一个拦截器不直接拦截？

答：因为系统里有一部分接口允许游客访问，比如场馆查询、热门动态、发送验证码、登录等，所以第一层只做身份恢复，不直接拦截，第二层再决定是否必须登录。

补一句高频细节就够了：

为了让业务代码方便获取当前登录用户，我会把用户信息暂存到 `ThreadLocal` 中，并在请求结束后清理，避免线程复用带来的用户串号问题。

### 1.4 这一块的简洁背诵版

我在项目里基于 Redis 实现了手机号验证码登录和 Token 登录态管理。用户请求验证码时，我会把验证码存入 Redis 并设置短 TTL；验证码校验通过后，生成随机 Token，把用户简要信息存入 Redis。后续请求进来后，先通过拦截器根据 Token 刷新用户信息并做续期，再通过登录拦截器判断当前接口是否必须登录。这样做更适合前后端分离和分布式部署场景。

## 3. 附近场馆检索

这一部分严格按照简历里的这句话来梳理：

基于 Redis GEO 实现附近球馆查询，支持按场馆类型和地理位置分页检索，提升本地生活场景下的查询效率。

所以只拆成 3 个点：

1. 为什么要用 GEO 做附近检索
2. 为什么要按场馆类型分桶存储
3. GEO 分页是怎么处理的

### 3.1 为什么要用 GEO 做附近检索

#### 背景阐述

这个项目里有“附近场馆检索”的需求，用户会希望按照自己的位置查看周边场馆。

这类场景和普通列表查询不一样，它不只是查“有哪些场馆”，而是要查“离我最近的有哪些场馆”。

#### 问题剖析

这里核心要解决的是“距离检索”问题。

常见思路一般有两种：

1. 直接用数据库做经纬度范围查询和距离排序；
2. 使用 Redis GEO 做空间位置检索。

如果完全依赖数据库来做，一般会有几个问题：

1. 距离计算和排序开销会比较大；
2. 在高频附近检索场景下，数据库压力会更明显；
3. 做实时附近查询，性能通常不如专门的空间索引结构。

#### 方案构思

所以我最终选择的是 Redis GEO。

Redis GEO 比较适合这个场景，原因主要有三个：

1. 它原生支持经纬度存储和范围检索；
2. 可以直接按距离排序，比较适合“附近的人/店/场馆”这类场景；
3. 查询性能更高，能减少数据库在高频地理检索场景下的压力。

所以从业务适配度来看，GEO 会比纯数据库方案更合适。

#### 复盘总结

所以这一点你可以总结成：

附近场馆检索本质上是一个地理位置检索问题，如果完全用数据库做距离计算和排序，性能压力会比较大。所以我最终选择了 Redis GEO 来承载附近查询能力，更适合本地生活场景。

#### 高频追问

问题：为什么不用数据库直接做附近查询？

答：数据库也能做经纬度查询，但距离计算和排序成本会更高，在高频附近检索场景下压力会比较明显。Redis GEO 原生支持地理位置检索和按距离排序，所以更适合这类本地生活场景。

### 3.2 为什么要按场馆类型分桶存储

#### 背景阐述

项目里不仅要查“附近场馆”，还要支持“按场馆类型筛选”，比如不同类型的场馆，需要在附近范围内继续细分。

所以这里不是单纯的附近检索，还带有类型过滤条件。

#### 问题剖析

如果所有场馆都放在同一个 GEO key 里，也能查附近数据，但类型过滤会比较麻烦。

常见思路一般有两种：

1. 所有场馆共用一个 GEO key，查出来之后再做类型过滤；
2. 按场馆类型分开存储，每种类型对应一个 GEO key。

第一种方案的问题是：

1. 先查附近再过滤，会拿出很多无效数据；
2. 类型越多，过滤成本越高；
3. 分页时还容易出现结果不稳定的问题。

#### 方案构思

所以我最终选择的是按场馆类型分桶存储。

也就是每种场馆类型维护一个独立的 GEO key，这样查询时可以直接定位到对应类型的数据集合，再结合用户坐标做附近检索。

这样做的好处是：

1. 查询范围更小；
2. 不需要拿到结果后再做大量类型过滤；
3. 类型筛选和地理检索可以天然结合，查询效率更高。

#### 复盘总结

所以这部分你可以总结成：

因为业务上不仅要查附近，还要按场馆类型筛选，所以我没有把所有场馆混在一个 GEO 集合里，而是按场馆类型分桶存储。这样可以减少无效扫描，也更适合分页查询。

#### 高频追问

问题：为什么不把所有场馆都放到一个 GEO key 里？

答：那样虽然也能查，但是类型过滤要放到查询结果之后再做，会带来很多无效数据，而且分页也不稳定。按类型分桶存储后，查询集合更小，效率和结果稳定性都会更好。

### 3.3 GEO 分页是怎么处理的

#### 背景阐述

附近检索通常不会一次把所有数据都返回，而是要支持分页，否则返回数据量过大，用户体验也不好。

#### 问题剖析

这里的难点在于：

Redis GEO 查询能按距离返回结果，但是不像mysql那样天然支持分页查询。

所以常见思路一般有两种：

1. 先把附近所有结果都查出来，再在应用层截取分页；
2. 先按分页需要的数量从 GEO 结果中取出当前页对应的 id，再去数据库查详情。

第一种方案在数据量上来后会比较浪费，因为每次都要拿很多并不会返回给用户的数据。

#### 方案构思

所以我这里采用的是“GEO 先查 id 和距离，数据库再查详情”的方式。

具体上，它的思路是：

1. 先根据当前页计算出需要的起始位置和结束位置；
2. 再从 GEO 结果中取出当前页对应范围内的场馆 id 和距离；
3. 然后用这些 id 去数据库查询详细信息；
4. 最后按照 GEO 返回的距离顺序组装结果。

这里的关键不是流程本身，而是这个分页思路：

我不会先把全部详情都查出来，而是先利用 GEO 做位置筛选和排序，再只取当前页真正需要的 id 去查数据库详情，这样能减少无效查询。

#### 复盘总结

所以这一点你可以总结成：

GEO 场景下分页的关键是先用 Redis 完成附近筛选和距离排序，再只拿当前页需要的 id 去数据库补充详情，并且按照原始距离顺序回填结果，这样既保留了附近检索能力，也控制了查询开销。

#### 高频追问

问题：为什么还要回数据库查一次，不能把场馆完整信息都放 GEO 里吗？

答：因为 GEO 结构更适合存地理位置信息和 member 标识，不适合承载完整业务详情。我的做法是让 Redis GEO 负责“找附近、排距离”，让数据库负责“补详情”，这样职责更清晰，数据维护也更方便。

### 3.4 这一块的简洁背诵版

我在项目里用 Redis GEO 做了附近场馆检索，因为这类本地生活场景本质上是地理位置检索，用数据库直接做距离计算和排序性能压力会更大。实现时我按场馆类型分桶存储地理坐标，这样查询时可以直接在对应类型集合里做附近检索，减少无效扫描。分页上，我先用 GEO 查出当前页需要的场馆 id 和距离，再回数据库补全详情并按距离顺序组装结果，这样兼顾了查询效率和结果准确性。

## 4. 社交动态流

这一部分严格按照简历里的这句话来梳理：

基于 Redis ZSet 实现球友动态点赞、关注推送与滚动分页查询，构建校园运动社交 Feed 流。

所以只拆成 3 个点：

1. 为什么点赞和 Feed 流要用 ZSet
2. 关注动态为什么选择推模式
3. 滚动分页为什么不用普通分页

### 4.1 为什么点赞和 Feed 流要用 ZSet 来存储

#### 背景阐述

这个项目里有明显的社交属性，用户可以发动态、点赞、关注别人，还可以查看自己关注球友的最新动态。

这类场景的共同特点是：

1. 数据天然带有时间顺序；
2. 需要快速判断用户是否点过赞；
3. 需要按时间倒序查看最新动态。

#### 问题剖析

这里核心要解决的是“有序存储”问题。

如果只把点赞用户或者动态 id 存到普通 `Set` 里，虽然能去重，但它不支持按时间顺序读取；如果每次都回数据库做排序，高频社交场景下压力又会比较大。


#### 方案构思

所以可以使用 Redis `ZSet`，把时间戳作为 score。

`ZSet` 比较适合这个场景，原因主要有三个：

1. 它本身支持去重；
2. 它可以通过 score 保存时间顺序；
3. 它支持按分数范围查询和排序，适合点赞列表和 Feed 流场景。


#### 复盘总结

所以这一点你可以总结成：

点赞和社交 Feed 流场景都需要“去重 + 有序 + 按时间查询”，普通 Set 或 List 都不够合适，所以我最终选择了 Redis ZSet，用时间戳作为 score 来维护顺序。

#### 高频追问

问题：为什么不用 List 或 Set，而要用 ZSet？

答：Set 只能去重，不能维护时间顺序；List 虽然有顺序，但不适合做快速去重和按 score 范围查询。ZSet 同时具备去重、有序、按分数范围查询的能力，所以更适合点赞和 Feed 流这类场景。

### 4.2 关注动态为什么选择推模式

#### 背景阐述

用户关注球友之后，通常更关心“我关注的人最近发了什么”，这就是典型的关注流场景。

这里本质上是在设计 Feed 流的数据分发方式。

#### 问题剖析

常见的 Feed 流实现一般有两种：

1. 拉模式，也就是用户打开页面时，再临时去查他关注的人发了哪些动态；
2. 推模式，也就是用户发动态时，直接把这条动态推送到粉丝的收件箱里。

拉模式的优点是写入轻，缺点是读的时候要临时聚合多个关注对象的动态，查询和排序的成本更高。

推模式的优点是读的时候很快，因为用户的收件箱数据已经提前准备好了；缺点是写扩散会更明显，也就是一个用户发动态时，要同步写给多个粉丝。

#### 方案构思

结合这个项目的场景，我最终选择的是推模式。

原因主要有两个：

1. 校园社交场景里，单个用户的粉丝量通常不会特别夸张，写扩散成本相对可控；
2. 用户看关注动态是高频操作，相比之下，提前推送到收件箱能显著降低读取时的聚合成本，提升体验。

所以我的做法是：当用户发布动态后，把这条动态 id 推送到所有粉丝对应的 `feed:userId` 这个 `ZSet` 中。

#### 复盘总结

所以这一点你可以总结成：

关注流场景在实现上有拉模式和推模式两种思路。考虑到校园场景下粉丝规模相对可控，而读取关注动态又是高频需求，所以我最终采用了推模式，把新动态直接推送到粉丝收件箱，换取更快的读取性能。

#### 高频追问

问题：为什么这里选择推模式，而不是拉模式？

答：因为这个项目更偏校园社交，粉丝规模相对可控，写扩散压力没有那么大；而用户查看关注动态是高频需求，所以我更倾向于把计算前置，提前推送到粉丝收件箱，换取更好的读取性能。

### 4.3 滚动分页为什么不用普通分页

#### 背景阐述

社交 Feed 流一般是按时间不断刷新的，用户更关心“最新的几条动态”，而不是固定的第几页。

所以这里的分页方式，和普通的那种页码分页不太一样。

#### 问题剖析

如果直接用普通分页，也就是 `pageNum + pageSize` 的方式，在 Feed 流场景里会有两个问题：

1. 数据持续插入时，页码会发生漂移，容易出现重复数据或者漏数据；
2. 如果多条数据时间戳相同，分页边界处理会比较麻烦。


#### 方案构思

所以不使用页码分页，选择滚动分页。

它的核心思路是：

1. 每次查询都带上一个 `max`，表示当前这次允许查询到的最大时间戳；
2. 同时带上一个 `offset`，表示 `max` 时间戳下，之前已经读取过多少条数据了，防止重复返回数据；
3. 查完之后返回新的时间戳和偏移量，供下一次继续往下翻。

这样做的好处是：

1. 更符合 Feed 流按时间连续下拉的交互方式；
2. 不容易因为新数据插入导致页码错乱；
3. 能比较稳定地处理相同时间戳数据的边界问题。

#### 复盘总结

所以这一点你可以总结成：

社交 Feed 流不适合传统页码分页，因为数据是持续变化的，容易出现翻页重复和漏数据问题。所以我采用了基于时间戳和偏移量的滚动分页，更适合按时间倒序不断下拉的社交流场景。

#### 高频追问

问题：为什么 Feed 流不用普通分页？

答：因为 Feed 流数据是持续变化的，如果用传统页码分页，在新数据不断插入时很容易出现数据重复或漏查。而滚动分页是基于时间戳继续往下查，更符合社交流场景，也更稳定。

### 4.4 这一块的简洁背诵版

我在项目里用 Redis ZSet 实现了社交动态流。之所以选 ZSet，是因为点赞和 Feed 流都需要同时满足去重、有序和按时间查询。关注动态分发上，我在拉模式和推模式之间选择了推模式，因为校园场景下粉丝规模相对可控，而用户读取关注动态是高频操作，提前推送到粉丝收件箱能显著提升读取性能。分页上，我没有用传统页码分页，而是采用基于时间戳和偏移量的滚动分页，更适合持续刷新的 Feed 流场景。

## 5. 高并发抢票与异步下单

这一部分严格按照简历里的这两句话来梳理：

针对校园赛事门票/热门活动名额集中抢领场景，使用 Lua 脚本在 Redis 中原子校验库存与一人一单，避免高并发下超卖和重复下单；

基于 Redis Stream 异步处理门票订单创建，结合 Redisson 分布式锁与全局唯一 ID 生成器提升高并发场景下的订单处理稳定性。

所以只拆成 4 个点：

1. 为什么要把抢票校验前置到 Redis
2. 为什么要用 Lua 保证原子性
3. 为什么要异步下单削峰
4. 为什么异步下单后还要加锁和做兜底

### 5.1 为什么要把抢票校验前置到 Redis

#### 背景阐述

这个项目里有校园赛事门票和热门活动名额的抢领场景，这类业务最大的特点就是流量会在短时间内集中爆发。

比如活动一开放，很多用户会同时点击抢票，如果所有请求都直接打到数据库，数据库很容易在瞬间被打满。

#### 问题剖析

这里核心要解决的是高并发流量下的数据库压力问题。

常见思路一般有两种：

1. 所有请求直接进数据库，做库存判断和下单；
2. 先在 Redis 层完成资格校验，再决定是否继续往下走。

如果所有请求都直接进入数据库，一般会有几个问题：

1. 数据库连接压力会非常大；
2. 大量无效请求也会进入数据库；
3. 在高并发场景下更容易出现超卖和响应变慢。

#### 方案构思

所以我最终选择的是把抢票资格校验前置到 Redis。

也就是先在 Redis 中做两件最核心的判断：

1. 库存是否还有剩余；
2. 当前用户是否已经下过单，也就是一人一单校验。

只有这两步都通过，才允许继续往后创建订单。这样可以把大量无效请求挡在数据库之前，大幅减轻数据库压力。

#### 复盘总结

所以这一点你可以总结成：

抢票场景下最大的风险是高并发请求集中打库，所以我把库存判断和一人一单校验前置到 Redis，先做快速过滤，减少数据库承压。

#### 高频追问

问题：为什么抢票场景要先走 Redis，不直接操作数据库？

答：因为抢票流量是短时间集中爆发的，如果所有请求都直接打数据库，数据库压力会非常大，而且很多请求本来就没有购买资格。把库存和重复下单校验前置到 Redis，可以先拦掉无效请求，显著降低数据库压力。

### 5.2 为什么要用 Lua 保证原子性

#### 背景阐述

在抢票场景里，库存判断和一人一单校验都属于并发敏感操作，只要这两个步骤之间出现并发穿插，就可能产生问题。

#### 问题剖析

这里常见的实现思路一般有两种：

1. 在 Java 代码里分多次调用 Redis，先查库存、再查是否下单、最后扣减库存；
2. 使用 Lua 脚本，把多个 Redis 操作封装成一个原子操作。

第一种方案的问题是：

1. 多条命令之间不是原子的；
2. 高并发下可能出现线程交叉，导致超卖或者重复下单；
3. 网络往返次数更多，性能也会差一些。

#### 方案构思

所以我最终选择的是 Lua 脚本方案。

我把下面几步操作放进了一段 Lua 脚本里：

1. 判断库存是否充足；
2. 判断用户是否已经下单；
3. 扣减库存；
4. 记录该用户已经下单；
5. 把订单信息发送到消息队列。

这样做的关键价值就在于：这些操作会在 Redis 内部一次性执行，天然具备原子性。

#### 复盘总结

所以这一点你可以总结成：

抢票场景里，库存校验和一人一单校验必须保证原子性。相比在 Java 里多次调用 Redis，我最终选择用 Lua 脚本把这些步骤封装成一个原子操作，从而避免超卖和重复下单。

#### 高频追问

问题：为什么 Lua 能解决超卖和重复下单问题？

答：因为 Lua 脚本在 Redis 中执行时是单线程原子执行的，库存判断、重复下单判断、扣库存和记录购买资格可以一次性完成，不会被其他线程插入，所以能避免并发穿透导致的超卖和重复下单。

### 5.3 为什么要异步下单削峰

#### 背景阐述

即使前面已经通过 Redis 过滤掉了很多无效请求，真正有购买资格的请求在高峰期依然可能很多。如果这些请求仍然同步创建订单、同步写数据库，系统吞吐还是会受到影响。

#### 问题剖析

这里核心要解决的是“抢票成功后的下单链路如何削峰”。

常见思路一般有两种：

1. 用户抢票成功后，立即同步创建订单；
2. 用户抢票成功后，先写入消息队列，再异步创建订单。

同步下单的缺点是：

1. 请求链路更长，接口响应更慢；
2. 高峰期数据库写入压力集中；
3. 瞬时吞吐能力更容易成为瓶颈。

#### 方案构思

所以我最终选择的是异步下单。

我的做法是：Lua 校验通过后，不是立刻在主线程里创建订单，而是先把订单信息写入 Redis Stream，然后由后台异步线程去消费消息、完成订单落库。

这样做的好处是：

1. 主流程只负责快速校验和入队，响应更快；
2. 把数据库写入压力从瞬时并发转换成可消费的队列流量；
3. 整个抢票链路具备更好的削峰填谷能力。

#### 复盘总结

所以这一点你可以总结成：

在高并发抢票场景下，我没有采用同步下单，而是把订单创建改成基于 Redis Stream 的异步处理。这样可以缩短主链路响应时间，同时把数据库写压力从瞬时并发转成平滑消费。

#### 高频追问

问题：为什么要异步下单，而不是同步落库？

答：因为抢票成功后的真实下单请求在高峰期依然很多，如果同步落库，接口响应时间和数据库压力都会比较大。异步下单可以把主流程和订单创建解耦，达到削峰填谷的效果。

### 5.4 为什么异步下单后还要加锁和做兜底

#### 背景阐述

异步化解决的是削峰问题，但并不代表后端消费订单时就完全没有并发风险了。

特别是在订单真正落库阶段，仍然需要关注一人一单和消息可靠处理问题。

#### 问题剖析

这里主要有两个风险：

1. 异步消费阶段仍然可能出现同一用户重复下单；
2. 消息消费异常时，如果没有兜底，可能会造成消息丢失或订单漏处理。

#### 方案构思

所以我这里又做了两层保障。

第一层是分布式锁。

我在消费订单时，会基于用户 id 加 Redisson 分布式锁，保证同一个用户的订单创建过程串行执行，进一步兜住一人一单问题。

第二层是消息兜底。

我使用的是 Redis Stream 的消费者组模式，消息处理成功后才会确认；如果处理异常，消息会进入 pending-list，后续再做补偿处理。

另外我还用了 Redis 生成全局唯一订单 id，这样在高并发场景下能够保证订单号生成效率和全局唯一性。

#### 复盘总结

所以这一点你可以总结成：

异步下单只是完成了削峰，但为了保证订单创建阶段的安全性，我又在消费端加了 Redisson 分布式锁来兜住一人一单问题，同时利用 Redis Stream 的 pending-list 机制处理异常消息，再配合全局唯一 ID 生成器保证订单生成稳定性。

#### 高频追问

问题 1：前面 Lua 已经判断过一人一单了，为什么消费端还要再加锁？

答：Lua 主要解决的是 Redis 侧的抢购资格校验，但订单真正落库时仍然属于异步消费阶段。为了避免极端并发或者重复消费带来的问题，我在消费端又基于用户 id 加了一层分布式锁，做进一步兜底。

问题 2：为什么选择 Redis Stream，而不是阻塞队列？

答：阻塞队列只适合单机内存场景，服务重启后数据容易丢失；Redis Stream 是持久化消息结构，支持消费者组、消息确认和 pending-list，更适合生产环境下的异步下单场景。

### 5.5 这一块的简洁背诵版

我在项目里针对校园赛事门票和热门活动名额抢领场景，做了一套高并发抢票方案。核心思路是先把库存判断和一人一单校验前置到 Redis，避免所有请求直接打库；再通过 Lua 脚本把库存校验、重复下单判断、扣库存和发送下单消息封装成原子操作，防止高并发下超卖和重复下单。订单创建阶段我没有采用同步落库，而是把订单信息写入 Redis Stream，由后台异步消费完成下单，实现削峰填谷。为了进一步保证稳定性，我在消费端又加了基于用户 id 的 Redisson 分布式锁，并利用 Stream 的 pending-list 做异常消息兜底，再配合 Redis 全局唯一 ID 生成器保证订单处理稳定。

## 6. 训练打卡

这一部分严格按照简历里的这句话来梳理：

基于 Redis Bitmap 实现训练打卡与连续打卡统计，降低签到类场景的存储成本。

所以只保留 2 个最高频点：

1. 为什么签到场景适合用 Bitmap
2. 连续签到统计为什么适合用位运算

### 6.1 为什么签到场景适合用 Bitmap

#### 背景阐述

这个项目里有训练打卡场景，用户会按天进行签到，后续还要查看自己的连续签到天数。

这类数据的特点很明显：

1. 按天记录；
2. 每天只有“签到”或“未签到”两种状态；
3. 数据量会随着用户数和日期不断累积。

#### 问题剖析

这里核心要解决的是“如何高效存储每日签到状态”。
常见思路一般有两种：

1. 用数据库签到表按天存记录；
2. 用 Redis Bitmap 按位存储签到状态。

#### 方案构思

我最终选择的是 Bitmap，而不是传统签到表。

原因很直接：

1. 一个 bit 就能表示一天的签到状态，存储非常紧凑；
2. 按天映射到位下标后，读写都比较直接；
3. 后续做连续签到统计时，也方便结合位运算处理。

如果这个场景更关注签到明细报表，数据库表会更直观；但我这个项目更关注高频签到和简单统计，所以 Bitmap 更合适。

#### 复盘总结

所以这一点你可以总结成：

训练打卡本质上是按天记录 0/1 状态的数据，和 Bitmap 的数据结构特点非常匹配，所以我最终选择了 Redis Bitmap 来存储签到状态，以降低存储成本。

#### 高频追问

问题：为什么签到场景适合用 Bitmap？

答：因为签到本质上就是每天是否签到的二值状态，非常适合用 bit 来表示。这样一个月的签到状态只需要少量位就能存下，存储成本比按天建记录低很多。

### 6.2 连续签到统计为什么适合用位运算

#### 背景阐述

训练打卡不只是记录今天签没签到，通常还会有一个很常见的需求，就是统计用户当前连续签到多少天。

#### 问题剖析

如果使用传统签到表来做连续签到统计，通常要按日期倒序查询，再逐天判断是否中断，逻辑会更重一些。

而在 Bitmap 方案下，签到状态本身就是一串连续的二进制位，所以天然可以考虑位运算。

#### 方案构思

我这里的做法是：

1. 先通过 `BITFIELD` 取出“从本月 1 号到今天”为止的签到状态；
2. 让这些签到状态以一个整数的形式返回；
3. 然后从最低位开始做位运算判断；
4. 连续遇到 1 就说明连续签到没有中断，计数器持续累加；
5. 一旦遇到 0，就说明连续签到中断，统计结束。

这个方案的关键点不是流程，而是思路：

我没有逐天回表查询，而是把连续签到问题转化成了一个二进制位连续统计问题。

#### 复盘总结

所以这一点你可以总结成：

在 Bitmap 方案下，连续签到统计很适合用位运算来做。我先把截止到今天的签到状态整体取出来，再从低位开始判断连续的 1 的个数，这样就能高效得到连续签到天数。

#### 高频追问

问题：为什么连续签到统计适合用位运算？

答：因为 Bitmap 存的本来就是一串二进制位，1 代表已签到，0 代表未签到。连续签到的本质就是从今天开始往前看连续有多少个 1，所以非常适合用位运算来处理。

### 6.3 这一块的简洁背诵版

我在项目里用 Redis Bitmap 做了训练打卡，因为签到本质上是按天记录的 0/1 状态，非常适合用 bit 位来表示。相比传统签到表，Bitmap 的存储成本更低，也更适合做高频签到场景。连续签到统计上，我没有逐天回表查询，而是先通过 BitMap 取出截止到今天的签到状态，再结合位运算统计从低位开始连续 1 的个数，这样可以高效得到连续签到天数。
