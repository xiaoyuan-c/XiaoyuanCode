# XiaoCode 项目亮点总结

## 项目定位

XiaoCode 不是一次调用大模型并展示答案的聊天 Demo，而是一个面向本地开发与个人学习场景的 AI Agent 运行时。它把用户目标、模型决策、工具执行、权限控制、上下文管理、事件展示和能力扩展串成了一条完整链路。

一句话概括：

> 我实现了一套本地 AI Agent 运行时：通过 ReAct Loop 驱动模型和工具协作，用独立权限层控制真实操作，用分层记忆、上下文压缩和 checkpoint 支撑长任务，再通过事件流、Skill、MCP、子 Agent 和个人知识库 RAG 扩展交互与能力边界。

## 亮点总览

| 亮点 | 解决的核心问题 | 关键词 |
| --- | --- | --- |
| 本地 Agent 运行时架构 | 客户端、任务执行和模型调用如何解耦 | daemon、CLI/TUI、回环 TCP、JSON-RPC、NDJSON |
| ReAct Loop 与稳定性治理 | Agent 如何连续决策，又不失控 | 推理—行动—观察、最大步数、取消、重复失败检测 |
| 长任务中断与断点续跑 | 进程中断或执行失败后如何安全继续 | 原子 checkpoint、运行状态、完整消息、待确认工具调用 |
| 统一工具调用与权限管理 | 模型如何安全地操作真实环境 | ToolRegistry、Pydantic、ToolResult、人工审批、差异化重试 |
| 上下文管理与分层记忆 | 长任务如何连续执行并控制上下文大小 | session、thread、notes、截断、compact |
| Skill、MCP 与子 Agent 扩展 | 如何扩展工作流、外部工具和协作能力 | Skill 白名单、MCP Tool、前台/后台 Subagent |
| 运行流程可观测 | 如何看到 Agent 正在做什么并定位问题 | EventBus、流式 token、events、trace、TUI |

# 一、本地 Agent 运行时架构

## 核心设计

项目采用 `kama-core` 常驻进程加 CLI/TUI 客户端的双进程结构。Core 负责会话、AgentLoop、工具、权限和持久化，客户端只负责发送命令和展示状态。

客户端与 Core 通过回环 TCP 长连接通信。命令请求和响应采用 JSON-RPC 2.0，通过请求 ID 完成关联；消息使用 NDJSON 分帧；Agent 执行事件则由 Core 在同一连接上主动推送。

## 设计价值

- 界面和任务执行解耦，TUI 退出不必直接等同于任务逻辑结束。
- CLI、TUI 以及未来的 Web 客户端可以复用同一个 Core。
- 命令响应和运行事件共享统一、类型化的通信边界。
- 权限审批、事件订阅和任务执行可以在同一连接上并发交互。

## 面试表达

> 我没有把模型调用直接写进界面，而是拆成常驻 Core 和客户端。Core 统一承载 Agent 运行时，客户端通过回环 TCP 与它通信，JSON-RPC 负责命令请求和响应，NDJSON 负责消息分帧，自定义事件负责持续推送执行过程。这种结构让运行逻辑不依赖具体界面，也方便后续增加新的客户端。

# 二、ReAct Loop 与稳定性治理

## 核心设计

AgentLoop 围绕“模型决策—执行工具—回填结果—再次决策”不断循环。模型负责判断下一步做什么，执行端负责保存上下文、调用工具和判断何时结束。

每次模型回复都会先作为 assistant 内容写入上下文；如果包含工具调用，系统按顺序执行工具，再把结构化结果作为 tool result 回填。模型返回正常结束状态时完成任务，否则继续下一轮。

## 稳定性设计

- 最大步数限制，防止模型一直调用工具而不结束。
- 模型和工具异常会转化为明确失败原因，而不是让任务静默卡住。
- 连续出现相同工具、参数和错误时，先要求重新规划，再继续重复则提前终止。
- 工具超时后区分“确定未执行”和“状态不明确”，避免盲目重试有副作用的操作。
- `CancelledError` 沿调用链向上传播，使任务可以按统一状态结束。

## 面试表达

> ReAct 的推理能力来自模型，我实现的是承载它的执行闭环。系统把模型回复、工具调用和工具结果组织成连续上下文，同时用最大步数、重复失败检测、超时状态确认和取消传播控制运行边界，所以它既能根据观察结果动态调整，也不会无限循环。

# 三、长任务中断与断点续跑

## 核心设计

每个 run 都会在自己的目录中维护 `checkpoint.json`。系统会在步骤开始、模型返回、工具开始、每个工具结果写入以及步骤结束等关键阶段原子更新 checkpoint，保存 run 状态、当前 step、完整模型消息、工具结果、待完成工具调用和恢复次数。

用户可在 TUI 中按 `Ctrl+G` 中断当前任务。中断或失败后，可通过 `/resume [session_id] run_id` 使用原 run ID 继续执行；daemon 重启后也能从磁盘重新加载 session 和 checkpoint。

## 安全恢复策略

如果系统在只读阶段中断，可以直接根据已保存上下文继续；如果恰好中断在写文件、执行命令等工具调用过程中，工具是否已经产生副作用无法可靠判断，因此不会自动重放。恢复时会补入一条“工具最终状态未知”的错误结果，并要求模型先检查当前状态，再决定是否重试。

## 面试表达

> 我给长任务增加了 run 级 checkpoint，在模型返回、工具执行前后和步骤完成等关键阶段原子持久化运行状态、模型消息和工具结果。任务取消、失败或 daemon 重启后，可以使用同一个 run ID 恢复。对于中断时状态不确定的副作用工具，我不会直接重放，而是把“不确定状态”回填给模型，让它先核验文件或外部状态，避免重复写入和重复执行。

# 四、统一工具调用与权限管理

## 核心设计

所有内建工具、MCP 工具、知识库工具和子 Agent 能力都进入统一工具注册表。工具向模型提供名称、描述和输入 Schema；模型发起调用后，执行端根据名称分发，并通过 Pydantic 参数模型进行运行时校验。

工具统一返回 `ToolResult`，其中包含结果内容、是否失败、错误类型和执行状态。这样 AgentLoop 不需要了解每种工具的内部实现，也能把成功或失败结果统一交回模型。

## 权限与错误治理

- 只读工具默认放行，Shell、文件写入等高风险操作默认需要确认。
- Shell 命令支持允许和拒绝规则，并检测工作目录越界行为。
- 用户可以选择单次允许、单次拒绝、会话复用或持久化授权。
- Schema、Runtime、Rate Limit、Timeout 等错误区别处理，不对所有错误机械重试。
- 限流采用有限次数的指数退避；参数错误直接交给模型修正。

## 面试表达

> 我把模型决策和真实操作隔开，所有工具都必须经过统一的注册、参数校验、权限检查和错误处理入口。提示词只能约束模型意图，权限层才真正控制操作能否执行。这样新增工具时不需要修改 AgentLoop，同时还能复用相同的安全和稳定性策略。

# 五、上下文管理与分层记忆

## 核心设计

项目把记忆分为会话、对话历史和笔记三个层次：

- `session` 关联同一段工作的多次 run。
- `thread` 保存用户消息、模型回复和工具结果，后续对话重新加入上下文。
- `notes` 保存需要长期保留的约束、结论和任务进度。

全局规则和项目规则则通过独立上下文文件注入系统提示，与动态对话历史分开管理。

## 上下文治理

- 过长的工具结果优先截断，避免单次输出占满上下文。
- 根据模型实际输入占上下文窗口的比例触发自动压缩，也支持手动压缩。
- 压缩时要求保留原始目标、关键决策、文件状态、剩余步骤和重要数据。
- 原始历史在替换前归档；已写入 notes 的关键内容会检查并补回摘要。

## 面试表达

> 我没有把记忆简单理解成不断拼接聊天记录，而是用 session 管理任务周期，用 thread 保存完整交互，用 notes 单独保存长期关键信息。上下文过长时先处理高噪声的工具输出，再按上下文占用比例调用模型生成任务摘要，从而兼顾连续执行和 token 成本。

# 六、Skill、MCP 与子 Agent 扩展

## Skill

Skill 使用 Markdown 描述适用场景、执行要求和工具白名单。既可以由用户手动触发，也可以把 Skill 名称和描述提供给模型，由模型判断是否激活。激活后不仅注入完整指令，还会收紧当前工具集合。

## MCP

项目作为 MCP 客户端，根据配置连接外部 MCP Server，完成初始化和工具发现，再把 MCP 工具包装成统一的 `BaseTool`。工具名称增加服务前缀以避免冲突，调用仍然复用原有的权限、超时、日志和结果回填流程。

## 子 Agent

子 Agent 的创建和结果查询也被封装成工具。子 Agent 使用独立上下文执行明确的子任务，并支持：

- 前台模式：主 Agent 等待结果后继续。
- 后台模式：先返回任务 ID，主 Agent 做其他工作，之后查询结果。
- 事件桥接：子 Agent 的执行过程进入父级事件体系，避免成为不可见黑盒。

## 面试表达

> Skill、MCP 和子 Agent 解决的是三类不同扩展：Skill 固化工作方法，MCP 接入外部能力，子 Agent 拆分独立任务。它们最终都接入现有工具和事件体系，因此扩展能力不会绕过权限、超时和可观测机制。

# 七、运行流程可观测

## 核心设计

项目把运行过程建模成类型化事件，包括 run、step、LLM token、工具调用、权限审批、上下文压缩和子 Agent 状态。EventBus 将同一份事件分发给不同消费者：

- TUI 实时展示 token、工具状态、权限卡片和上下文占用。
- `events.jsonl` 保存单次 run 的业务事件，可用于回放。
- trace 记录 IPC、EventBus 和 LLM 三层数据流，用于跨层定位问题。

LLM 的流式文本先转换成 `llm.token` 事件，再通过回环 TCP 长连接以 NDJSON 推送给 TUI；TUI 持续累积 token，结束后统一渲染成 Markdown。

## 面试表达

> 我没有只保存普通日志，而是把 Agent 生命周期建模成结构化事件。同一份事件既能驱动 TUI 实时展示，也能持久化和回放；再配合 IPC、事件和 LLM 三层 trace，可以判断问题发生在客户端通信、内部调度还是模型调用阶段。

# 八、个人知识库 RAG

## 核心设计

项目把 Obsidian Markdown 仓库作为只读知识源，按标题层级切分笔记，并保留文件路径、标题路径和标签。索引和缓存全部保存在 XiaoCode 的 `workspace` 目录，不修改原始 Obsidian 仓库。

检索链路包括：

```text
BM25 关键词召回 + BGE Embedding / Faiss 向量召回
    → RRF 排名融合
    → 笔记级候选筛选
    → BGE Reranker 重排
    → Top-K 片段交给模型
```

检索工具支持同义表达和查询改写；复杂问题由现有 AgentLoop 根据第一次结果继续检索和综合。索引更新使用文件哈希识别变化，只为新增或修改的片段生成向量，再重建统一索引。

## 面试表达

> 为了让 Agent 利用我的个人学习笔记，我增加了只读 Obsidian RAG。关键词检索负责精确术语，向量检索补充语义召回，RRF 融合两路排名，再用 Reranker 精排。检索被封装成统一工具，因此模型可以在 AgentLoop 中改写查询和多轮检索，同时继续复用原有权限、事件和上下文机制。

# 推荐的面试讲解顺序

如果面试官让你整体介绍项目，可以按下面顺序组织：

1. 先说明它是本地 Agent 运行时，而不是一次性 LLM 调用。
2. 介绍 ReAct Loop，解释 Agent 如何连续决策和执行。
3. 介绍 checkpoint 与安全恢复，体现长任务的工程可靠性。
4. 介绍工具运行时与权限层，体现工程安全和扩展性。
5. 介绍分层记忆与上下文压缩，体现长任务治理能力。
6. 根据面试官兴趣，展开事件可观测、Skill/MCP/子 Agent 或 RAG。

最值得重点讲的三项是：

1. ReAct Loop 与稳定性边界。
2. 长任务 checkpoint 与安全恢复。
3. 统一工具运行时与独立权限层。
4. 分层记忆与上下文治理。

其他能力用于证明这套核心架构具有可观测性和可扩展性，而不是彼此孤立的功能堆砌。

# 表述边界

- ReAct 的推理不是自己训练的，项目实现的是模型推理与工具执行之间的运行闭环。
- Shell 规则和人工审批用于降低风险，但不能等同于完整的操作系统沙箱。
- checkpoint 能恢复执行上下文，但无法凭空判断中断瞬间外部副作用是否已发生，因此必须先核验状态，不能宣称任意工具都能无损重放。
- LLM 压缩通过笔记保护和历史归档降低信息损失，不能宣称完全无损。
- RAG 已完成真实索引和检索验证，但尚未通过大规模评测证明效果提升，后续应使用 Recall@K、MRR 和延迟进行量化。
