# XiaoCode 模拟面试（CV 精简版）

围绕 CV 中 XiaoCode 的项目概述和五条描述，共 14 问。各部分保留 CV 原文，问题侧重场景、方案和取舍，回答按面试口述组织。已实现的能力以当前项目代码为准，后续改进会明确说明。

# 项目概述

## 问：简单介绍一下 XiaoCode，主要解决什么问题？

XiaoCode 是一个面向本地开发任务的 AI Agent，用户给出目标后，它可以读取文件、修改代码、执行命令，并根据结果继续完成后面的步骤。

我主要解决了三个问题：一是让 Agent 能连续执行任务，并在失败或反复尝试时有退出边界；二是对工具调用统一做校验和权限控制，尤其是执行命令、修改文件这些操作；三是管理长任务的上下文，让它能接着之前的工作继续。除此之外，我还做了能力扩展和子 Agent 协作，执行过程也会展示和记录，方便定位问题。

# 一、ReAct 闭环

> CV：实现「推理—行动—观察」执行闭环，解析模型文本 / Tool Use / 终止状态；通过最大步数、异常中断、取消信号避免循环失控。

## 问：任务的执行流程是怎么设计的？为什么这样设计？

我采用的是 ReAct，也就是让模型根据当前信息决定下一步，执行工具后，再根据结果调整后续行动。

因为本地开发任务很难一开始就把所有步骤定死。比如排查一个问题，通常要先读代码、运行命令，看到结果后才能决定怎么改。所以我让工具的成功结果和失败信息都回到模型的上下文里，让它根据实际情况继续决策。模型负责选择行动，执行端负责校验、权限和退出条件，这样既保留了灵活性，也能控制实际操作。

## 问：你遇到过 Agent 死循环吗？当时是怎么处理的？

> 场景草稿，实际经历待核实；此备注不属于口述回答。

遇到过。我的文件写入工具漏了自动创建父目录，Agent 往新目录写文件时一直报错，收到错误后还是反复提交同样的请求。我看调用日志、单独复现后，定位到了这个问题，补上目录创建逻辑并做了验证。另外，执行循环有最大步数限制，一直不结束就终止任务并记录原因。这次让我意识到，工具报错能给模型调整的机会，但不能保证它会调整，还得由执行端限制步数来兜底。

## 问：你如何防止 Agent 陷入死循环？

- **最大步数兜底**：模型正常结束就退出；一直不结束，达到步数上限就终止任务并记录原因。
- **超时和有限重试**：工具调用设置超时，重试也有次数限制，避免单次操作一直卡住或反复执行。
- **错误反馈**：把失败原因交回模型，让它调整参数或换方案。
- **重复失败检测**：连续 3 轮都是相同工具、相同参数和相同错误，就提醒模型重新规划；再重复失败 2 轮，就提前结束并记录原因。成功调用或工具、参数、错误变化会重置计数，正常轮询不会触发这条规则。

## 问：任务执行到一半出错或者要停止，你怎么处理？

我会区分单个操作失败和整个任务无法继续。

工具失败时，先把原因交回模型，让它改参数或者换方案；
模型调用遇到部分网络中断，会先有限重试，如果最终仍然失败，就结束任务，保留执行记录和失败原因。

停止任务时，我希望执行端先记录任务已经取消，再把取消传递给上层。

# 二、统一工具运行时

> CV：基于工具注册表 + Pydantic Schema 做注册、校验与分发，工具返回结果结构化回注上下文；将 Schema / Runtime / Rate Limit / Timeout 四类异常拆分、差异化重试，提升长链路稳定性。

## 问：工具注册、校验与分发怎么做的？

- **注册**：每次 Agent Loop 开始时，以工具名称为键、工具对象为值构建注册表，再从中提取名称、描述和参数定义，组成结构化的工具列表发送给模型。
- **校验**：模型返回调用后，先检查工具是否存在；对配置了参数模型的工具，用 Pydantic 校验参数等，不合法就返回错误。
- **分发**：根据名称找到对应工具，通过统一入口完成权限检查再去执行，再把结果返回给本次调用，交回模型继续处理。

## 问：模型调用工具这块，你是怎么设计的？

我把模型决策和工具执行分开了。模型只需要知道工具能做什么、需要什么参数，真正的调用通过统一入口处理。这样新增工具时，主要是接入工具本身，核心任务流程不需要跟着改。

内建工具在执行前会再次校验参数，再经过权限检查和执行。
返回时，成功内容和失败原因都用统一的方式交回模型，让它知道刚才的操作有没有完成、接下来需要调整什么。
这样工具增加以后，校验、权限、超时和错误处理也能继续复用。

## 问：工具调用失败了怎么办？你会一直重试吗？

我会先看失败原因。

- 参数不合法，或者工具根本不存在，重复执行同一个请求没有意义，就把错误交回模型，让它修正。
- 执行过程中报错，会进行有限重试，如果还是错误，把错误返回给模型，让它修改方案。
- 被限流时会采用指数退避拉长等待时间，再有限重试；
- 超时后先暂停修改，检查实际状态：已完成就不重复执行，确认没生效才重试，部分完成或状态不明就停止。

# 三、工具权限控制

> CV：在工具调用前引入独立权限层，针对 Shell、文件写入等高风险行为做命令规则匹配、工作目录越界检测、异步人工审批，支持单次 / 会话级 / 持久化授权。

## 问：讲解一下，你的权限控制怎么做？

我在工具真正执行前设置了一层独立的权限检查，统一决定直接放行、拒绝，还是交给用户确认。因为模型可能理解错任务，单靠提示词不能保证实际操作符合用户的意图，可能产生一些高危操作

一些无害操作是可以直接放行的，比如读取文件、查看目录这种只读操作，
但是修改文件和执行命令这种高危命令需要确认。
其实很多危险操作都是在shell命令中的，命令还可以配置允许和拒绝规则；
如果疑似访问工作目录以外的位置，即使之前授权过，也会再次要求确认。
用户确认前，这次操作不会执行，拒绝或审批超时就返回失败，让模型调整方案。

## 问：每次操作都要用户确认吗？怎么兼顾安全和使用效率？

不需要所有操作都确认。我把默认的读取操作直接放行，把审批放在执行命令、修改文件这些风险较高的操作上。
用户可以只允许当前这次操作，也可以对后续操作选择始终允许，减少重复打断。

# 四、分层上下文

> CV：构建会话 / 线程 / 笔记三层上下文，超长工具返回结果截断；基于上下文占用比例触发 LLM 压缩，压缩时保留任务目标、关键决策、文件状态与剩余步骤，支撑长任务连续执行。

## 问：说说你的agent记忆是怎么设计的？

我主要按会话、对话历史和笔记三层来设计。会话把同一段工作的多次执行关联起来；对话历史保存用户要求、模型回复和工具结果；笔记由 Agent 主动保存需要需要长期记忆的约束和结论。这些都存到本地文件里，同一个会话下一轮执行时，会重新加载历史和笔记，让它能接着之前的工作继续。另外，全局和项目的固定规则会从配置文件加载到系统提示里。

为了控制上下文大小，我会截断过长的工具输出。如果历史上下文太长时再压缩成摘要，重点保留任务目标、关键决策和剩余步骤。

## 追问：上下文压缩成摘要是怎么做的？压缩的提示词怎么写？

上下文压缩可以通过命令手动触发，可以达到上下文占用阈值自动触发。每轮工具执行结束、任务还要继续时，会检查上下文占用比例，达到阈值就触发压缩。

单独调用一次模型去生成摘要。提示词会明确告诉它：“后续模型只能根据这份摘要继续任务，请按如下要求蒸馏出摘要：原始目标、已完成步骤、关键约束和发现、当前文件状态、剩余任务，以及必须原样保留的数据。省略中间推理和尝试，保留结论，文件路径、错误信息和配置值要准确。”生成成功后，用摘要替换当前历史；调用失败或摘要为空，就保留原来的上下文。

## 上下文压缩如果丢失了一些关键信息，怎么办？

我复用了已有的笔记机制，让 Agent 把重要约束和任务进度存到笔记里，新保存的内容会立即进入当前上下文。压缩时会读取最新笔记，逐条检查摘要有没有原样保留笔记正文，遗漏的由执行端补回，再替换历史。

原始消息也会在替换前归档，摘要里带上归档路径，方便发现信息缺失时回读；如果归档失败，就不替换历史。不过这只能保护已经写入笔记的内容，哪些信息需要保存仍由 Agent 判断，也没有做语义一致性检查，所以不能保证摘要完全无损。

## 问：用户接着上一次任务继续问，你怎么让 Agent 记住之前的内容？

我把这部分分成会话、对话历史和笔记。会话负责把同一段工作的多次执行关联起来；对话历史保存用户要求、模型回复和工具结果，下一次继续时加载进去；笔记单独保存需要长期记住的事实和结论，比如已经确认的约束。

这样既能知道前面具体做过什么，也能单独保留关键结论。历史会不断增长，笔记可以减少后续反复查找重要信息的成本。当前笔记由 Agent 主动保存，加载历史时也会截断过长的工具结果，避免单条输出占用太多上下文。

# 五、子 Agent 协作与能力扩展

> CV：用 Skill 模板注入系统指令与工具白名单，把 MCP Tool 包装为统一工具基类，将子 Agent 的创建与结果回传注册进工具注册表；支持子 Agent 独立上下文、前台 / 后台执行、事件桥接与结果查询。

## 你的 Skill 是怎么触发的？

我支持手动和自动两种触发方式。手动通过命令指定。自动触发时，会把可用 Skill 的名称和描述放进一个激活 skill 的工具的说明里，随工具列表一起发给模型。模型判断任务匹配后，就调用这个工具，用参数指定 Skill 名称和任务目标。

执行端收到调用后，载入完整 skills；如果配置了工具白名单，也会同步收紧可用工具。后序轮次，模型就按照这个 Skill 的指令继续执行，仍然经过原来的权限检查。

## 问：系统中的 Skill 是怎么写的？

用 Markdown 文件编写，分成头部配置和正文。头部写名称、适用场景、工具白名单等元信息。其中描述要写清楚什么时候用，方便模型判断。正文描述具体应该怎么做，以及最终结果的输出要求。

## 问：你怎么扩展 Agent 的能力？

我分成三种情况。常见任务需要固定的步骤和输出要求，就用 Skill 提供做法，并限定可用工具；需要连接外部工具，就通过 MCP 接入；需要把一块独立工作拆出去，就交给子 Agent。

比如代码审查可以通过 Skill 约定检查重点和输出格式，外部系统的能力可以通过 MCP 引入，单独分析一个模块则可以作为子任务。工具接入和子任务调用都复用统一的执行入口，这样权限控制、超时和结果反馈能沿用已有方案，核心任务流程不需要为每种扩展重新设计。

## 问：什么样的任务适合交给子 Agent？拆出去可能存在什么问题？

目标清楚、依赖较少、能单独给出结果的任务适合交给子 agent，比如分析某个模块或者审查一组文件。
主 Agent 交代目标、约束和必要背景，子 Agent 用自己的上下文执行，完成后再把结论交回来。小任务直接由主 Agent 做，避免额外的模型调用和协调成本。

独立上下文可以减少无关信息，但也意味着任务描述必须完整，否则子 Agent 容易缺少背景。另外，当前父子 Agent 共享本地文件，独立上下文并不等于文件隔离。涉及修改文件时，需要明确各自负责的范围

## 问：主 Agent 怎么和子 Agent 配合，怎么拿到结果？

系统把子 Agent 的创建和结果查询都封装成了工具。主 Agent 调用工具，传入子任务的目标、约束和必要背景。如果下一步依赖子任务的结果，就采用前台执行，工具等待子任务完成后直接返回结果；如果不依赖，就采用后台执行，先返回 ID，主 Agent 继续做其他工作，之后调用工具去查询是否完成并获取结果。

## 讲一下项目中的 MCP 是怎么做的？

项目里我实现的是 MCP 客户端。启动时按配置连接服务，完成初始化后获取工具的名称、描述和参数定义，再包装成统一工具，和内建工具一起提供给模型。模型选中后，客户端向 MCP 服务发送调用请求，把结果交回模型，权限检查、超时和日志都复用原来的执行流程。

本地服务主要通过 stdio，也就是标准输入输出通信，另外也实现了自定义的 TCP 连接。工具名会加上服务名前缀，避免不同服务的工具重名。目前主要接入的是工具能力。
