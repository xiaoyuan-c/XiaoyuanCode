# XiaoCode 模拟面试（CV 精简版）

仅围绕 CV 中 XiaoCode 的项目概述和五条描述，共 12 问。回答以当前 main 分支实现为准，可直接作为面试口述；简历中需要收紧的表述在对应位置注明。

# 项目概述

## 问：简单介绍一下 XiaoCode，主要解决什么问题？

XiaoCode 是一个面向本地开发任务的 AI Agent Runtime，让模型通过工具操作文件、执行命令，并根据执行结果继续完成任务。我主要围绕三个问题做设计：用 ReAct 和退出条件约束长任务，用统一工具运行时和权限层控制真实操作，用分层上下文和压缩缓解上下文膨胀。在此基础上，通过 Skills、MCP 和子 Agent 扩展能力。执行过程会产生结构化事件，实时展示并持久化记录，便于排查问题。

# 一、ReAct 闭环

> CV：实现「推理—行动—观察」执行闭环，解析模型文本 / Tool Use / 终止状态；通过最大步数、异常中断、取消信号避免循环失控。

## 问：为什么选择 ReAct？这个闭环在项目中怎么体现？

本地开发任务经常需要读完文件或看到命令结果，才能确定下一步，因此我选择根据工具结果不断调整的 ReAct。模型根据上下文决定行动，运行时保存模型回复；如果有工具调用，就执行并把结果写回上下文，供下一轮决策。一轮可以调用多个工具，一个任务可以循环多轮，直到模型返回结束状态。

## 问：怎样防止 Agent 一直死循环？LLM 异常和取消怎么处理？

正常情况下根据模型的 `end_turn` 结束；最大步数负责兜底，防止模型反复尝试却没有进展。LLM 调用异常会终止任务，工具失败一般作为错误结果交回模型，让它调整方案。
底层收到 `asyncio` 取消后，会记录取消状态并向上传播。

这里的“取消信号”指底层异步取消处理，当前还没有给用户提供完整的停止按钮或取消命令。

# 二、统一工具运行时

> CV：基于工具注册表 + Pydantic Schema 做注册、校验与分发，工具返回结果结构化回注上下文；将 Schema / Runtime / Rate Limit / Timeout 四类异常拆分、差异化重试，提升长链路稳定性。

## 问：为什么需要统一工具运行时？Pydantic 和结构化结果各有什么作用？

我希望新增工具时不需要修改 Agent Loop，所以用统一工具基类定义接口，再由注册表按名称查找和分发。

工具的 JSON Schema 告诉模型怎么传参，内建工具执行前再用 Pydantic 校验，避免把模型生成的错误参数直接拿去执行。

成功结果和失败结果都统一封装成 `ToolResult`；回填模型时携带结果内容和失败标记，并关联原来的工具调用，让模型知道工具执行是否成功，决定下一步怎么做。

## 问：四类错误为什么要区别处理？什么情况会重试？

区别处理的原因是：不同错误的恢复方式不同，重复执行不一定有用，还可能产生副作用。我根据错误能否通过重试恢复，以及重复执行的风险来选择策略，避免无效重试，同时给暂时性故障保留恢复机会。

- **Schema 错误**：工具参数不合法，同样的参数再次执行也没用，因此不自动重试，让模型根据错误重新生成参数。
- **Runtime 错误**：部分执行错误是暂时性的，有限重试可能恢复。当前使用同一工具、同一份参数最多额外重试两次，仍失败再把错误结果回填给 LLM；找不到工具等执行前错误直接失败。
- **Rate Limit 错误**：遇到限流错误，暂时限制请求，立即重试容易再次被限流，因此采用指数退避，逐渐拉长等待时间，等待恢复。
- **Timeout 错误**：工具未在规定时间内完成，而且可能已执行一部分。自动重试可能重复操作，因此当前直接反馈失败，让 LLM 调整方案。


# 三、工具权限控制

> CV：在工具调用前引入独立权限层，针对 Shell、文件写入等高风险行为做命令规则匹配、工作目录越界检测、异步人工审批，支持单次 / 会话级 / 持久化授权。

## 问：为什么权限层要独立？具体怎么限制高风险操作？

提示词只能引导模型，实际执行仍需要系统把关。
因此我把权限检查放在工具调用前，统一决定放行、拒绝或请求审批。
默认读取类工具直接放行，Shell 命令和文件写入需要审批；Shell 还支持允许、拒绝规则匹配，疑似越出工作目录的命令会强制请求审批。

## 问：异步人工审批怎么做？2种授权范围都实现了吗？

需要审批时，runtime 发送审批事件，由客户端界面展示操作内容，然后等待用户决定。
等待期间当前工具不会执行，事件循环仍可以处理其他事情；
用户的决定通过客户端命令传回，命令与响应采用 JSON-RPC 2.0。
当前支持单次授权和持久化授权。单次授权只允许这次工具调用，但“始终允许”会同时写入缓存和持久化文件，后续遇到相同工具调用根据缓存或持久化结果自动判断。

# 四、分层上下文

> CV：构建会话 / 线程 / 笔记三层上下文，超长工具返回结果截断；基于上下文占用比例触发 LLM 压缩，压缩时保留任务目标、关键决策、文件状态与剩余步骤，支撑长任务连续执行。

## 问：会话、线程、笔记分别存什么？为什么要分开？

- **会话 Session**：管理会话状态，关联多次任务运行。
- **线程 Thread**：记录对话历史，保存用户消息、模型回复和工具结果，在后续对话上加载到上下文中，让Agent能够接着之前的内容继续
- **笔记 Notes**：Agent 主动保留的值得长期保存的事实和结论，后续运行时加载到上下文。

这样可以分别管理会话状态、详细过程和关键结论。完整历史会持续增长，把关键结论单独保存，有利于后续继续任务。

另外，重新加载历史时会截断过长的工具结果，减少单条结果占用的上下文空间。

## 问：“基于上下文占用比例触发压缩”是什么意思？压缩时如何保留任务目标、关键决策、文件状态和剩余步骤？

意思是根据上下文用了多少空间决定是否压缩。项目用最近一次 LLM 调用返回的输入 token 数，除以代码中设定的模型上下文窗口大小，估算占用比例。例如阈值设为 80%，达到阈值且任务还需继续时，就在本轮工具结果回填后调用 LLM 生成摘要，为后续执行腾出空间。
保留关键信息主要靠固定的摘要提示词：把历史消息交给 LLM，明确要求按指定结构总结出摘要，用这段摘要替代原来的完整信息


# 五、子 Agent 协作与能力扩展

> CV：用 Skill 模板注入系统指令与工具白名单，把 MCP Tool 包装为统一工具基类，将子 Agent 的创建与结果回传注册进工具注册表；支持子 Agent 独立上下文、前台 / 后台执行、事件桥接与结果查询。

## 问：Skills、MCP、子 Agent 分别解决什么问题？为什么接入同一套工具体系？

Skill 预先写好任务的做法、步骤和输出要求，加载为系统指令来指导 LLM，并通过白名单限制可用工具。总的来说，为一些常见的任务提供解决流程指南

MCP 用来接入外部工具，适配成统一工具基类后进入注册表；

子 Agent 则把独立子任务交给另一个执行上下文完成，创建和结果查询也暴露成工具。

这样可以复用已有的工具分发、权限检查和结果回填逻辑，Agent Loop 不需要为每种扩展单独写一套流程。需要区分的是，MCP 工具复用外部提供的 Schema，当前没有对应的本地 Pydantic 参数模型。

## 问：为什么子 Agent 使用独立上下文，不直接继承全部历史？

子任务通常只需要一部分信息，复制全部历史会增加上下文开销，也容易引入无关内容。我让子 Agent 从明确的任务描述开始，维护自己的消息历史和运行状态，完成后把结果返回主 Agent。

代价是主 Agent 必须交代清楚目标、约束和必要背景。这里隔离的是模型上下文，父子 Agent 仍共享本地文件环境，并不具备文件系统隔离。

## 问：前台、后台执行怎么选？结果和进度怎么回到主 Agent？

如果主 Agent 下一步必须依赖子 Agent 的任务结果，就前台等待，完成后直接以工具结果返回。如果子任务可以独立推进，就用 `asyncio` 创建后台任务，先返回子任务运行 ID，主 Agent 继续工作，之后通过结果查询工具获取状态和最终结果。

子 Agent 的事件会转发到父级事件总线，让客户端展示子任务进度。这种“事件桥接”负责进度展示，主 Agent 获取后台最终结果仍依靠结果查询工具。
