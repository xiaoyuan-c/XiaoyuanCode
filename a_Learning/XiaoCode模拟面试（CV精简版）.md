# XiaoCode 模拟面试（CV 精简版）

按当前仓库实现重新组织。主线是：**连续执行 → 失败治理 → 安全续跑 → 上下文续航**，再根据追问展开架构、可观测性、扩展能力和 RAG。每题先练口述回答，再根据追问补充设计取舍和实现边界。

> 下文的 CV 均为建议表述；“我”的负责范围应按实际经历调整。代码和测试能证明实现行为，不能证明个人贡献或线上效果，不把假设场景说成亲历事故。

## 一、项目介绍与整体架构

### 1. 问：用一分钟介绍一下 XiaoCode。

XiaoCode 是一个面向本地开发和个人学习的 AI Agent 运行时。用户给出目标后，它可以读取文件、修改代码、执行命令，并根据工具结果继续决定下一步。

系统采用常驻 Core 加 TUI 客户端的结构，CLI 用于脚本测试和调试。Core 负责模型调用、工具、权限、会话和持久化，TUI 展示执行过程并接收用户审批。

我会重点介绍四部分：ReAct 连续执行、工具调用的校验与权限、长任务中断后的 checkpoint 恢复，以及分层记忆和上下文压缩。Skill、MCP、子 Agent 和只读 Obsidian RAG 都接在这套运行链路上。

### 2. 问：为什么拆成 daemon 和客户端？它们怎么通信？

主要是把界面交互和任务执行的生命周期分开，让多个客户端复用同一个执行内核。代价是需要处理通信协议、连接管理和异步状态同步。

当前使用回环 TCP 长连接，NDJSON 用换行划分 JSON 消息；命令与响应采用 JSON-RPC 2.0，用请求 ID 关联，运行事件通过自定义事件消息主动推送。Pydantic 为命令和事件定义类型边界。

服务端把请求交给独立异步任务处理，所以长任务等待模型或审批时，同一连接仍能处理审批响应和取消命令。同一 session 则通过锁限制并行执行，避免两次 run 同时改写历史。

**追问：TUI 退出后任务一定继续吗？**

任务由 Core 承载，客户端断开不必直接导致整个 Core 停止，但审批等待、连接清理和取消仍有各自规则。准确说法是执行与界面解耦，不能承诺所有断连场景都无影响。

## 二、ReAct 闭环与稳定性

> CV：实现 ReAct 执行闭环，将模型回复、工具调用与工具结果组织为连续上下文；通过最大步数、取消传播和重复失败检测控制运行边界。

### 3. 问：一次任务具体怎么执行？为什么选择 ReAct？

用户目标先进入执行上下文。每轮调用模型，把回复写入历史；如果模型请求工具，就按顺序执行，并把成功内容或错误结果按调用 ID 回填，再进入下一轮。模型返回正常结束状态时，运行时结束任务。

代码排查很依赖中间结果，例如先读文件、运行测试，再决定怎么改。ReAct 能让后续决策吸收这些观察，适合这种路径不能提前完全确定的任务。模型提供决策能力，项目实现的是承载模型和工具交互的运行闭环。

**追问：模型说完成了，就一定完成了吗？**

当前主要按模型终止状态判断成功；超时恢复尚未确认时会阻止成功结束，但没有通用的任务验收器。更严格的任务需要把测试、文件检查等验收条件纳入流程。

### 4. 问：怎么防止 Agent 一直循环？

首先有最大步数兜底，模型异常和取消也会结束运行。其次会检测重复失败：只有一整轮工具全部失败，而且工具名、参数、错误类型和内容构成的失败指纹相同，才累计连续轮数。

默认连续 3 轮相同失败时注入重新规划要求，再重复 2 轮就提前终止。成功调用或失败指纹变化会重置计数。同一次工具调用内部的重试不算新一轮，正常返回“仍在运行”的轮询也不会算失败。

这能识别一类“没有新信息的重复尝试”，但不能识别所有无效循环，所以最大步数仍然需要保留。

### 5. 问：任务执行到一半要停止，你怎么处理？

TUI 的 Ctrl+G 会向 Core 请求取消当前 run。执行端取消异步任务，Runner 完成状态记录、历史保存和 checkpoint 落盘，再把取消向上传递；取消接口会等待相关收尾完成后响应。

Shell 工具收到取消时还会尝试清理进程树。这里必须区分“停止继续执行”和“撤销已经发生的操作”：文件可能已经改过，取消不会自动回滚。

## 三、长任务 checkpoint 与安全续跑

> CV：在模型返回、工具执行前后和步骤结束等阶段原子保存 run 级 checkpoint，支持主动中断及 daemon 重启后续跑；对中断时结果缺失的工具调用补齐未知状态，避免自动重放。

### 6. 问：已经有会话历史，为什么还要 checkpoint？

会话历史用于下一次对话继续交流；checkpoint 用于恢复同一次尚未完成的 run。只有历史，未必知道运行停在哪一步、哪些工具结果已写入、哪些调用还没拿到结果。

checkpoint 保存原 run ID、目标、阶段、状态、step、完整消息、待完成工具调用、终止原因和恢复次数等信息。它在模型返回、工具开始、每个工具结果回填以及步骤完成等关键位置更新。

写入时先写同目录临时文件，flush 和 fsync 后再用 os.replace 覆盖，降低写到一半破坏原 checkpoint 的风险。这个原子更新只保护快照文件，不构成与外部工具副作用之间的事务。

### 7. 问：程序重启后，怎么恢复任务？

用户通过 TUI 的 /resume [session_id] run_id 指定要恢复的运行。Core 从磁盘加载 session 和 checkpoint，校验二者的 ID 对应关系，恢复消息和步数，继续使用原 run ID，并记录恢复事件。已经成功的 run 不允许再次恢复。

恢复依靠已保存的执行信息重新进入模型决策，不是从某一行 Python 指令继续执行，也不是重放所有历史工具调用。

### 8. 问：如果文件已经写成功，但结果还没保存，恢复时会重复写吗？

这个时间窗口是恢复设计的关键：checkpoint 与文件修改不是同一笔事务，所以缺少结果不能证明工具没执行过。

当前实现对所有没有配对结果的 pending 调用都保守处理：补一条“最终状态未知”的错误结果，并提示模型先检查当前文件或外部状态，再决定下一步；不会自动重放，也没有单独为只读调用做重放分支。

这降低了盲目重复执行的风险，但还不能保证任意工具只执行一次。恢复阶段主要依赖错误回填和核验提示；更强保证需要工具提供幂等键、状态查询或操作记录。

## 四、统一工具运行时与权限

> CV：通过 ToolRegistry、参数模型和统一调用入口完成工具分发、权限检查、超时及分类重试；以独立权限层控制 Shell 和文件写入，支持异步审批与授权复用。

### 9. 问：新增一种工具，需要改 AgentLoop 吗？

通常不用。工具实现统一的 BaseTool 接口，提供名称、描述、输入 Schema 和 invoke 方法，再注册进 ToolRegistry。模型选择工具后，统一入口查找工具、校验参数、检查权限、限时执行，最后返回 ToolResult。

ToolResult 包含内容、失败标记、错误类型，以及可选的执行停止状态。Loop 只需要处理统一结果，不必了解每种工具内部如何工作。

**追问：所有工具都经过本地 Pydantic 校验吗？**

配置了 params_model 的工具会进行本地校验。MCP 工具直接使用服务端提供的 input_schema，当前包装器没有本地 Pydantic 参数模型，不能说所有外部工具都获得同样的本地校验保证。

### 10. 问：工具报错时，哪些能重试，哪些不能？

| 情况 | 当前处理 |
| --- | --- |
| 参数校验失败、未知工具 | 直接回填错误，让模型修正 |
| Runtime Error、Rate Limit | 默认最多重试 2 次，等待按指数退避增长 |
| 权限拒绝 | 返回失败，不在同一次调用中继续重试 |
| Timeout | 不直接自动重试，先处理执行状态 |
| 超时后已确认的一次重试 | 只执行一次，不叠加内部重试额度 |

重试策略也有边界：当前普通 Runtime Error 仍按统一策略重试，没有全面按副作用和幂等性细分。Shell 非零退出前可能已经产生修改，因此不能宣称所有错误重试都安全。后续应让工具明确是否可重试，并区分瞬时错误和业务失败。

### 11. 问：为什么超时不能直接重试？你具体怎么确认？

超时只说明没及时拿到结果，不说明操作没有生效。对于有副作用的工具，系统记录待确认状态，阻止后续修改操作，只允许只读检查和 resolve_tool_timeout。

模型先检查实际状态，再提交本次超时之后成功的检查调用 ID 作为依据：确认完成就禁止重复；确认未生效时，若进程清理没有被标记为失败，则给一次重试额度；部分完成、状态未知、清理无法确认，或者重试后再次超时，则停止恢复。重试仍然经过正常权限检查。

执行端校验检查依据是否存在、是否来自超时后的成功只读调用，但不独立理解这些结果能否证明“已完成”。状态结论仍由模型判断，这是当前机制的边界。

**追问：它和 checkpoint 恢复有什么区别？**

超时恢复是本次运行内的状态机，有检查依据和执行限制。checkpoint 恢复是在进程中断后补齐调用结果、重新进入决策。当前 checkpoint 没有完整持久化超时恢复状态机，不能把两者说成同一种强制恢复保证。

### 12. 问：权限层如何兼顾安全和效率？

权限检查发生在实际执行前。read_file、list_dir 等已登记的读取工具默认放行；bash、write_file 和未登记工具默认要求审批。

Shell 先匹配拒绝规则，再检查疑似工作目录外访问；命中越界启发式时强制要求确认，既有允许规则和授权缓存不能绕过。其余情况再看授权缓存、允许规则和工具默认策略。

需要审批时，Core 发出结构化事件并等待 Future，TUI 提交决策后再继续；拒绝或审批超时都不会执行工具。单次授权只作用于当前调用；“始终允许/拒绝”按工具名写入会话缓存，并在配置了策略文件时持久化，不是对某一条精确命令的授权。

**追问：这相当于文件系统沙箱吗？**

它是规则匹配和审批层。当前越界检测主要是 bash 命令的正则启发式，不是覆盖所有工具的路径隔离；复杂 Shell 表达式也可能超出规则识别范围。操作系统隔离和更细的授权粒度属于后续改进。

## 五、分层记忆与上下文压缩

> CV：以 session、thread、notes 管理会话与长期关键信息；截断超长历史工具结果，按上下文占用触发摘要压缩，并通过笔记补回和历史归档降低信息丢失风险。

### 13. 问：session、thread、notes 分别解决什么问题？

session 关联同一段工作的多次 run，并管理状态；thread 保存用户消息、模型回复和工具结果，下一轮继续时重新加载；notes 单独保存 Agent 主动记录的重要约束、结论和进度。

全局规则和项目规则则通过固定上下文文件加入系统提示。它们与动态会话历史分开，不需要每次让用户重复输入。

notes 需要 Agent 主动保存，并不是系统自动识别全部重要事实；RAG 则检索外部学习笔记，解决的是另一类知识访问问题。

### 14. 问：什么时候压缩？压缩以后模型靠什么继续？

加载历史时会截断超长的工具结果，减少单条输出的占用。运行中在一轮工具结果回填完成、任务还要继续时，根据 Provider 上报的输入 token 与模型窗口的比例检查配置阈值。项目配置默认关闭自动压缩；把 auto_threshold 设为 0.8 后，达到 80% 会触发，也支持手动压缩。

压缩单独调用模型，要求摘要保留六类内容：原始目标、已完成步骤、关键约束与发现、当前文件状态、剩余任务和必须准确保留的数据。成功后用摘要和确认消息替换当前历史，让下一轮从摘要继续。

这个比例是当前实现的水位信号，依赖模型窗口配置和用量口径，并非对下一轮新增工具输出的精确预测。

### 15. 问：如果摘要漏掉用户约束，怎么办？

压缩器读取最新 notes，按笔记正文检查摘要是否原样包含，遗漏的由执行端补回。替换历史前还会归档完整原消息，并把归档路径写进摘要，必要时可以回读。

模型调用失败、摘要为空、笔记读取失败或历史归档失败时，都保留原上下文。但这只能直接保护已经保存的笔记；摘要其他部分没有语义一致性校验，所以不能保证完全无损。notes 也会增长，后续需要去重和容量管理。

## 六、事件流与问题定位

> CV：将运行、模型、工具、审批和压缩过程建模为类型化事件，统一驱动 TUI 与事件持久化；通过 IPC、EventBus、LLM 三层 trace 定位链路问题。

### 16. 问：为什么要 EventBus，普通日志不够吗？

运行过程需要被界面和持久化逻辑同时消费，所以我把 run、step、token、工具和审批状态定义成结构化事件。EventBus 将事件交给 TUI 推送、events.jsonl 写入等订阅者，执行逻辑不必分别处理每个展示端。

例如权限审批需要客户端识别工具、参数和调用 ID 并返回决策，单纯打印日志无法承担这套交互。LLM 的流式文本也会转成 token 事件，TUI 累积内容，结束后渲染 Markdown。

**追问：慢订阅者会拖慢任务吗？**

会。当前 EventBus 按注册顺序依次 await，IPC 广播也会等待连接 drain。设计简单、顺序清楚，但没有独立消费队列和完整的慢客户端隔离。负载增大时，需要考虑有界队列、背压和消费者异常隔离。

### 17. 问：用户说“任务卡住了”，你怎么排查？

先按 run ID 看最后一个业务事件，判断卡在模型调用、工具执行还是权限等待。再结合工具耗时、错误类型和尝试次数，以及 checkpoint 的阶段、pending 调用，确认执行进度。

如果 TUI 没展示状态，就沿 trace 检查 LLM 是否产生回复、EventBus 是否发布事件、IPC 是否推送到客户端。events 用于还原业务过程，trace 用于定位跨层数据流；事件回放本身不会重新执行工具。

## 七、Skill、MCP 与子 Agent

> CV：以 Skill 注入任务指令和工具白名单，将 MCP 工具包装为统一接口；以独立上下文子 Agent 承担子任务，支持前台等待、后台查询与事件桥接。

### 18. 问：Skill 是怎么触发的？只是加一段提示词吗？

既支持用户手动指定，也支持模型调用 activate_skill 自动激活。自动触发时先只把可用 Skill 的名称和描述提供给模型，模型判断匹配后再加载完整正文，避免一开始塞入所有指令。

激活后会设置本轮任务的系统指令，并按 allowed_tools 收紧注册表。白名单只保留已有工具，不会凭空增加权限；保留下来的工具仍经过原有审批。当前一次 run 最多自动激活一个主要 Skill。

### 19. 问：MCP 是怎么接入的？和 Skill 有什么区别？

项目作为 MCP 客户端，按配置连接服务，完成 initialize、工具发现和调用，再把服务端工具包装为 BaseTool。名称加服务前缀避免冲突，执行继续复用统一权限、超时、事件和结果回填。

当前有 stdio 和项目自定义 TCP 连接，主要接入工具能力，没有宣称完整覆盖所有 MCP 能力或传输方式。Skill 规定“任务怎么做”，MCP 提供“能调用什么外部能力”。

### 20. 问：哪些任务适合拆给子 Agent？结果怎么回来？

适合目标明确、依赖较少、能独立交付结论的任务，例如分析某个模块或审查指定文件。子 Agent 冷启动独立上下文，只收到父 Agent 提供的任务描述，所以目标、约束和必要背景必须写完整。

前台模式等待完成后直接返回；后台模式先返回 run ID，父 Agent 继续做其他工作，再通过 agent_result 查询。子事件会桥接到父事件体系，便于展示执行进度。

代价是额外模型调用、背景传递和协调成本。父子 Agent 共享本地文件，独立上下文不等于文件隔离；当前没有自动解决并发写冲突，后台任务查询也主要依赖进程内注册表。

## 八、只读 Obsidian RAG

> CV：接入只读 Obsidian 知识库，按标题层级分块，采用 BM25 与 BGE/Faiss 混合召回、RRF 融合及可选 Reranker；通过统一检索工具支持查询扩展和多轮检索，按文件哈希复用未变化笔记的向量。

### 21. 问：为什么加 RAG？从笔记到回答的流程是什么？

本地 Agent 已经能操作项目文件，我希望它也能利用个人积累的学习笔记。RAG 把外部知识访问封装成工具，让模型在需要时检索，并拿到可引用的来源。

索引端只读扫描 Markdown，解析标题和标签，按标题层级切分；过长段落再按字符长度切分并保留重叠。检索端的流程是：

```text
原查询 + 可选改写
  → BM25 关键词召回 + BGE / Faiss 向量召回
  → RRF 融合
  → 可选的笔记级候选筛选
  → 可选的 BGE Reranker 重排
  → Top-K 片段及来源 → AgentLoop 综合回答
```

knowledge_search 返回片段 ID、路径、标题层级和正文；knowledge_read 按 ID 读取索引中的完整片段。来源信息方便核对，但并不自动保证模型回答忠实于原文。

### 22. 问：为什么用混合召回和 RRF？Faiss 用的什么索引？

BM25 提供关键词匹配，向量检索补充表达不同但语义相关的候选。它们的原始分数含义不同，所以采用 RRF 累加各路的 1 / (k + rank)，用排名融合，当前默认 k 为 60。

之后可用 Reranker 对原查询和候选正文重新打分。它只处理有限候选，以控制成本；但重排无法找回召回阶段已经漏掉的内容，因此需要分别评估召回和排序。

当前 Faiss 使用 IndexFlatIP，生产向量会归一化，内积排序等价于余弦相似度排序。它是精确检索，实现简单，适合当前个人知识库规模；还没有实现 HNSW 或 IVF 近似索引。

### 23. 问：查询改写、层级检索和 Agentic RAG 具体体现在哪里？

检索工具允许传原查询和最多 4 个改写表达，各次召回结果统一融合。工具提供的是改写入口，改写内容由调用方或模型生成，没有独立自动改写模块。

层级筛选是在片段召回后，按来源笔记聚合，用该笔记最高片段分数选候选笔记，再保留这些笔记的候选片段重排。它利用了标题和笔记结构，但不是先检索笔记摘要、再全量检索正文的两级索引。

Agentic RAG 则复用现有 Loop：模型可以根据第一次结果调整查询，再次检索并综合回答。当前没有单独的检索规划器，也不保证每个问题都会自动多轮检索。

### 24. 问：笔记更新后怎么办？“增量索引”增量在哪里？

索引器重新扫描并计算文件哈希。文件和分块配置都没变化时跳过构建；部分文件变化时，复用未变化文件已有片段的向量，新建或修改文件的片段重新生成向量，删除文件不再进入新索引。

最终 BM25 和 Faiss 索引仍会整体重建，因此更准确的说法是“增量复用 Embedding”，不是只对向量索引做局部增删，也不是修改一个文件就只计算其中改动的一小段。模型变化时不能直接复用旧模型的向量。

源笔记只做读取，索引默认保存在项目的 workspace/rag/obsidian 目录。这是 RAG 模块的数据访问边界，不代表其他通用 Shell 或写文件工具也被系统级禁止访问知识库。

### 25. 问：你怎么证明 RAG 有提升？结果不相关怎么办？

当前代码具备分块、关键词检索、工具接入等测试，但不能仅凭测试或一次回答就给出检索效果提升百分比。需要整理真实问题、期望命中的笔记或片段，建立固定评测集。

我会分别比较 BM25、向量检索、混合检索，以及是否加入改写、层级筛选和重排，记录 Recall@K、MRR 和检索延迟；再检查回答的引用是否支持结论。候选数与重排开关需要根据这组结果调整。

检索结果差时，先区分没召回到、排序靠后，还是模型使用了错误内容。可以调整查询和路径/标签过滤后再次检索；缺乏依据时应说明知识库未提供足够支持。当前没有基于校准分数的通用拒答阈值。

## 九、综合场景与收尾问题

以下是基于实现的推演练习，不代表本人实际遇到过这些事故。

### 26. 问：Agent 改文件的命令超时了，随后用户中断任务并重启 Core，你怎么办？

先区分两个时间窗口。如果工具已经返回超时结果，本轮会进入超时状态检查；如果用户在结果保存前中断，恢复时会看到没有配对结果的 pending 调用。

重启后用 checkpoint 恢复上下文，先检查文件、差异和相关进程状态，再决定剩余工作。不能因为超时或中断就假定修改没发生，也不能把之前只存在内存中的超时检查依据当成已完整恢复。确认不清楚或发现部分修改时，应报告现状，避免盲目重复执行。

### 27. 问：用户先说不能改配置文件，任务压缩后又交给子 Agent，你怎么保留这条约束？

主 Agent 应把约束保存进 notes，压缩时通过笔记补回机制保留。派生子任务时还要明确把这条约束写进 prompt，因为子 Agent 不继承父级对话历史。

如果子任务只需要分析，应使用限制写工具的角色配置。提示词传递意图，工具白名单和权限检查提供执行约束；当前还没有通用的按文件路径禁止修改策略，不能仅靠一句提示承诺绝不误改。

### 28. 问：项目最有技术含量的部分是什么？还想改什么？

我会重点讲长任务的失败与恢复边界。模型、工具和文件副作用发生在不同阶段，不能把“报错”直接等同于“没执行”，也不能把“有历史”直接等同于“可安全续跑”。checkpoint、未知结果补齐和运行内超时检查，就是围绕这些状态差异设计的。

下一步我会优先完善副作用工具的幂等与重试策略，补齐恢复所需状态的持久化，再做事件消费者隔离和 RAG 固定评测。这些改进分别对应重复执行风险、恢复信息缺失、慢客户端影响，以及检索效果缺乏量化证据。

### 29. 问：你怎么验证项目？哪些效果目前不能证明？

仓库里已有 Loop、重试、权限、checkpoint、压缩和 RAG 工具等单元测试，以及真实 daemon 与客户端通信的集成测试。模型和工具 stub 可以稳定构造“副作用发生但结果丢失”“超时后重复修改”“压缩遗漏笔记”等边界，避免完全依赖模型随机输出。

这些测试验证工程行为；模型任务完成率、真实知识库召回效果和大规模并发性能，需要另设评测和运行实验。面试前应记录实际运行过的检查结果，不把“存在测试文件”说成“全部测试已经通过”。
