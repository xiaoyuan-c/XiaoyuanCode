# XiaoCode 模拟面试（CV 精简版）

只保留简历相关的高频问题。回答时先说结论，再补一句原因，不主动展开无关细节。

## 一、项目与架构

### 1. 问：介绍一下 XiaoCode。

XiaoCode 是一个面向本地开发和个人学习的 AI Agent 助手。用户给出目标后，它可以读取文件、修改代码、执行命令，并根据工具结果继续完成任务。

我主要实现了 ReAct 执行闭环、工具权限控制、长任务断点续跑和上下文管理，并接入了 Skill、MCP、子 Agent 和 Obsidian RAG。

### 2. 问：为什么拆成 daemon 和客户端？

为了把界面和任务执行解耦。Core daemon 负责模型、工具和任务状态，CLI、TUI 等客户端只负责发送命令和展示过程。

### 3. 问：客户端和 Core 怎么通信？

通过回环 TCP 长连接通信，消息格式是 JSONL；命令和响应使用 JSON-RPC 2.0，运行事件由 Core 主动推送给客户端。

### 4. 问：TUI 关闭后任务会怎样？

正常按 `Ctrl+Q` 退出时，会先取消当前任务并保存 checkpoint，后续可以通过命令继续运行。若客户端意外断开，Core 不会随界面一起退出，任务可能继续运行。

## 二、ReAct 与运行稳定性

### 5. 问：一次任务是怎么执行的？

每轮先调用模型。模型如果请求工具，系统就执行工具，把结果写回上下文，再让模型继续判断；模型返回正常结束状态时，任务完成。

### 6. 问：为什么使用 ReAct？

因为代码任务的下一步通常取决于刚得到的结果。例如先读文件、运行测试，才能决定怎么修改。ReAct 能让模型根据观察结果继续决策。

### 7. 问：怎么防止 Agent 一直循环？

首先设置最大步数；
其次检测重复失败。相同工具以相同参数连续失败时，先要求模型重新规划，继续重复就提前终止。

### 8. 问：怎么主动取消任务？

用户在 TUI 按 `Ctrl+G`，Core 会取消当前 run，并保存运行状态、消息和 checkpoint。

取消只会停止后续执行，不会撤销已经发生的文件修改。

## 三、长任务 checkpoint

### 9. 问：已经有会话历史，为什么还要 checkpoint？

会话历史用于下一次聊天；checkpoint 用于恢复同一次未完成的 run。它会额外记录运行阶段、step、模型消息、工具结果和待处理的工具调用。

### 10. 问：checkpoint 在什么时候保存？

在步骤开始、模型返回、工具开始、工具结果写入和步骤完成时保存。写入采用临时文件加原子替换，避免文件只写了一半。

### 11. 问：程序重启后怎么恢复任务？

用户通过 `/resume [session_id] run_id` 指定任务。Core 加载磁盘中的 session 和 checkpoint，恢复消息与步数，再使用原 run ID 继续执行。

### 12. 问：恢复时会不会重复执行工具？

已经有结果的工具不会重放。如果工具开始执行但结果没保存，系统会把它标记为“最终状态未知”，让模型先检查当前状态，而不是直接重试。

因为没有结果不代表没有执行，直接重放写文件或 Shell 命令可能造成重复修改。

## 四、工具调用与权限

### 13. 问：新增工具需要修改 AgentLoop 吗？

不需要。工具实现统一接口并注册到工具注册表，AgentLoop 只处理统一的工具调用和工具返回。

### 14. 问：工具 Schema 和 Pydantic 分别做什么？

工具 Schema 告诉模型有哪些工具以及参数格式；Pydantic 在真正执行前校验模型传入的参数。

当前配置了参数模型的本地工具会用 Pydantic 校验，MCP 工具主要使用服务端提供的 `input_schema`。

### 15. 问：不同工具错误怎么处理？

工具参数错误，不重试，直接返回给模型修改；
运行时报错有限重试；
限流错误就是采用指数退避策略等待，防止立即重试又被限流
工具权限被拒绝了，不重试，返回给模型重新生成方案；
工具执行超时的话，先检查实际状态，再决定是否重试，如果已经成功了，就不重试了；如果完全没生效，就尝试重试；如果部分完成或状态不明，就停止重试

### 16. 问：为什么超时不能直接重试？

因为超时只表示没有及时拿到结果，不代表工具没有执行。系统会先让模型用只读工具检查状态，再决定是否重试。

### 17. 问：工具权限怎么控制？

权限检查发生在工具真正执行前。读取文件等只读工具默认允许，Shell 和写文件默认需要用户确认。

用户可以单次允许或拒绝，也可以保存按工具生效的规则。这是审批机制，不是操作系统级沙箱。

## 五、上下文管理

### 18. 问：session、thread、notes 分别是什么？

- `session`：一段连续会话，可以包含多个 run。
- `thread`：保存用户消息、模型回复和工具结果。
- `notes`：保存需要长期保留的约束、结论和任务进度。

### 19. 问：上下文压缩什么时候触发？

一轮工具执行完成后，如果任务还要继续，系统会检查上下文占用比例。达到配置阈值时自动压缩，也可以手动触发。

### 20. 问：压缩后怎么继续任务？如果摘要遗漏怎么办？

系统把历史压缩成摘要，保留任务目标、已完成工作、关键约束、文件状态和剩余步骤，再让模型从摘要继续。

`notes` 中遗漏的内容会自动补回，压缩前历史也会归档。但摘要仍不能保证完全无损。

## 六、可观测性

### 21. 问：为什么使用 EventBus，而不是只写日志？

因为同一份运行状态既要实时展示给 TUI，也要写入事件文件。EventBus 可以把结构化事件分发给不同消费者。

普通日志适合阅读，但不能直接承担权限审批、工具状态和流式 token 等程序交互。

### 22. 问：用户说任务卡住了，你怎么排查？

先根据 run ID 查看最后一个事件和 checkpoint，判断停在模型、工具还是权限审批阶段。

如果 Core 有事件但 TUI 没显示，就检查 EventBus 和 IPC；如果模型没有返回，就检查 LLM trace。

## 七、Skill、MCP 与子 Agent

### 23. 问：Skill、MCP 和子 Agent 有什么区别？

Skill 规定一类任务应该怎么做；MCP 接入外部工具；子 Agent 把独立子任务交给另一个 Agent 执行。

它们最终都接入现有的工具和事件体系。

### 24. 问：Skill 是怎么生效的？

Skill 可以由用户手动触发，也可以由模型根据名称和描述选择。激活后会注入完整任务说明，并通过工具白名单限制本次可用工具。

### 25. 问：MCP 工具怎么接入？

项目作为 MCP 客户端连接外部 MCP Server，获取工具列表，再把工具包装并注册到 `ToolRegistry`。

### 26. 问：什么任务适合子 Agent？

目标明确、依赖较少、可以独立交付结果的任务适合子 Agent，例如分析一个模块或审查指定文件。

子 Agent 有独立上下文，但与主 Agent 共享本地文件，所以并行修改同一文件仍可能冲突。

## 八、Obsidian RAG

### 27. 问：为什么增加 RAG？完整流程是什么？

为了让 Agent 能使用我的 Obsidian 学习笔记。系统只读扫描 Markdown，按标题切分，然后执行下面的检索流程：

`BM25 关键词召回 + BGE/Faiss 向量召回 → RRF 融合 → 可选 Reranker → Top-K 片段交给模型`

### 28. 问：为什么同时使用 BM25、向量检索和 RRF？

BM25 擅长准确关键词，向量检索擅长语义相近的表达。两种分数不能直接相加，所以使用只依赖排名的 RRF 融合结果。

### 29. 问：查询改写、层级检索和 Agentic RAG 怎么实现？

查询改写允许模型提交多个查询一起检索；层级检索先根据片段选择相关笔记，再重排笔记内片段；Agentic RAG 让模型根据第一次结果再次检索。

这些能力复用现有 AgentLoop，没有单独实现另一套 RAG Agent。

### 30. 问：笔记变化后怎么更新索引？

通过文件哈希判断变化。未变化文件复用原向量，新增或修改文件重新生成向量，最后重建 BM25 和 Faiss 索引。

所以更准确地说是“增量复用 Embedding”，不是向量索引的局部更新。

### 31. 问：怎么证明 RAG 有提升？

需要建立固定问题集，对比 BM25、向量检索和混合检索的 Recall@K、MRR 与延迟。

当前检索链路已经实现，但不能宣称经过大规模评测证明效果提升。

## 九、综合问题

### 32. 问：项目最有技术含量的部分是什么？

我会重点讲长任务的状态管理。模型调用、工具执行和文件副作用处于不同阶段，不能把“报错”直接理解成“没有执行”。

checkpoint、超时状态检查和未知结果补齐，都是围绕这个问题设计的。

### 33. 问：项目还可以怎么改进？

进一步为副作用工具增加幂等控制，持久化更完整的恢复状态，隔离慢事件消费者，并建立固定的 RAG 评测集。

### 34. 问：项目怎么测试？

单元测试覆盖 Loop、重试、权限、checkpoint、压缩和 RAG；集成测试覆盖真实 daemon 与客户端通信。

这些测试能证明工程行为，但不能直接证明模型任务完成率、RAG 实际提升幅度或大规模并发性能。

## 十、面试表达边界

### 35. 问：哪些话不能说得太满？

- 不说“中断后无损恢复”，应说“恢复上下文，并保守处理状态未知的工具调用”。
- 不说“超时就是没执行”，应说“超时后先确认实际状态”。
- 不说“权限层等于沙箱”，应说“规则和审批用于降低风险”。
- 不说“上下文压缩完全无损”，应说“通过 notes 补回和历史归档降低损失”。
- 不说“RAG 已显著提升效果”，应说“检索链路已实现，效果需要评测证明”。
