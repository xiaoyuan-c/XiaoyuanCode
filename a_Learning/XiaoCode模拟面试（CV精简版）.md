# XiaoCode 模拟面试（CV 精简版）

围绕 CV 中 XiaoCode 的项目概述和五条描述，共 14 问。各部分保留 CV 原文，问题侧重场景、方案和取舍，回答按面试口述组织。已实现的能力以当前项目代码为准，后续改进会明确说明。

# 项目概述

## 问：简单介绍一下 XiaoCode，主要解决什么问题？

XiaoCode 是一个面向本地开发任务的 AI Agent，用户给出目标后，它可以读取文件、修改代码、执行命令，并根据结果继续完成后面的步骤。

我主要解决了三个问题：一是让 Agent 能连续执行任务，并在失败或反复尝试时有退出边界；二是对工具调用统一做校验和权限控制，尤其是执行命令、修改文件这些操作；三是管理长任务的上下文，让它能接着之前的工作继续。除此之外，我还做了能力扩展和子 Agent 协作，执行过程也会展示和记录，方便定位问题。

# 一、ReAct 闭环

> CV：实现「推理—行动—观察」执行闭环，解析模型文本 / Tool Use / 终止状态；通过最大步数、异常中断、取消信号避免循环失控。

## 问：任务的执行流程是怎么设计的？为什么这样设计？

我采用的是 ReAct，也就是让模型根据当前信息决定下一步，执行工具后，再根据结果调整后续行动。

因为本地开发任务很难一开始就把所有步骤定死。比如排查一个问题，通常要先读代码、运行命令，看到结果后才能决定怎么改。所以我让工具的成功结果和失败信息都回到模型的上下文里，让它根据实际情况继续决策。模型负责选择行动，执行端负责校验、权限和退出条件，这样既保留了灵活性，也能控制实际操作。

## 问：你遇到过 Agent 死循环吗？当时是怎么处理的？

我在工具失败后的恢复测试里构造过这类场景：用模拟的模型回复持续请求一个不存在的工具。每次调用都会失败，错误也会交回模型，但下一轮还是同样的无效请求，形成了反复尝试的循环。

我的处理是设置最大执行步数。正常情况下，模型给出结束状态就退出；如果一直不结束，达到步数上限就终止任务，并记录失败原因。测试也验证了这个边界。工具错误反馈能给模型修正的机会，但还需要执行端的步数限制来兜底。

## 问：只限制步数够吗？有没有更好的办法？

步数上限能防止无限执行，但发现问题比较晚。针对刚才的场景，我会补充重复失败检测：记录工具、参数和返回结果，如果连续几轮都是相同调用、相同错误，就给模型一次重新规划的机会，要求它调整方案；调整后仍然没有进展，就提前结束并说明卡在哪里。

判断时还要结合是否获得了新信息、结果是否发生变化，避免把正常的重复读取或状态轮询误判成死循环。当前项目已经有错误反馈和最大步数限制，重复失败检测以及受限的重新规划，是后续可以补充的改进。

## 问：任务执行到一半出错或者要停止，你怎么处理？

我会区分单个操作失败和整个任务无法继续。工具失败时，先把原因交回模型，让它改参数或者换方案；模型调用遇到部分网络中断，会先有限重试，如果最终仍然失败，就结束任务，保留执行记录和失败原因。

停止任务时，我希望执行端先记录任务已经取消，再把取消传递给上层。目前项目支持底层异步任务的取消处理，但还没有完整的用户停止入口。后续会补一个停止当前任务的操作，让用户可以主动中断执行。

# 二、统一工具运行时

> CV：基于工具注册表 + Pydantic Schema 做注册、校验与分发，工具返回结果结构化回注上下文；将 Schema / Runtime / Rate Limit / Timeout 四类异常拆分、差异化重试，提升长链路稳定性。

## 问：模型调用工具这块，你是怎么设计的？

我把模型决策和工具执行分开了。模型只需要知道工具能做什么、需要什么参数，真正的调用通过统一入口处理。这样新增文件工具或外部工具时，主要是接入工具本身，核心任务流程不需要跟着改。

内建工具在执行前会再次校验参数，再经过权限检查和执行。返回时，成功内容和失败原因都用统一的方式交回模型，让它知道刚才的操作有没有完成、接下来需要调整什么。这样工具增加以后，校验、权限、超时和错误处理也能继续复用。

## 问：工具调用失败了怎么办？你会一直重试吗？

我会先看失败原因。参数不合法，或者工具根本不存在，重复执行同一个请求没有意义，就把错误交回模型，让它修正。被限流时会拉长等待时间，再有限重试；执行过程中报错，也会限制尝试次数。超时则直接反馈失败，因为操作可能已经执行了一部分，马上重试容易重复操作。

重试后仍然失败，会把结果交回模型，让它调整方案。当前执行错误的重试策略还比较粗，后续我会根据工具能否安全重复执行来决定是否重试，尤其是修改文件和执行命令这类可能产生副作用的操作。

# 三、工具权限控制

> CV：在工具调用前引入独立权限层，针对 Shell、文件写入等高风险行为做命令规则匹配、工作目录越界检测、异步人工审批，支持单次 / 会话级 / 持久化授权。

## 问：Agent 能执行命令、改文件，你的权限控制怎么做？

我在工具真正执行前设置了一层独立的权限检查，统一决定直接放行、拒绝，还是交给用户确认。因为模型可能理解错任务，单靠提示词不能保证实际操作符合用户的意图。

默认读取文件、查看目录可以直接执行，修改文件和执行命令需要确认。命令还可以配置允许和拒绝规则；如果疑似访问工作目录以外的位置，即使之前授权过，也会再次要求确认。用户确认前，这次操作不会执行，拒绝或审批超时就返回失败，让模型调整方案。这里的越界判断是基于命令特征的风险识别，当前还没有严格的文件系统沙箱。

## 问：每次操作都要用户确认吗？怎么兼顾安全和使用效率？

不需要所有操作都确认。我把默认的读取操作直接放行，把审批放在执行命令、修改文件这些风险较高的操作上。用户可以只允许当前这次操作，也可以对后续操作选择始终允许，减少重复打断。

这里需要说明授权范围：当前“始终允许”按工具类型记录，同时用于当前会话和后续会话，并不是只授权某一条命令，也还没有独立的“仅本会话允许”选项。拒绝规则和疑似越界检查仍然会优先生效。后续我会把授权范围细化到命令或目录，让用户能更明确地控制放开哪些操作。

# 四、分层上下文

> CV：构建会话 / 线程 / 笔记三层上下文，超长工具返回结果截断；基于上下文占用比例触发 LLM 压缩，压缩时保留任务目标、关键决策、文件状态与剩余步骤，支撑长任务连续执行。

## 问：用户接着上一次任务继续问，你怎么让 Agent 记住之前的内容？

我把这部分分成会话、对话历史和笔记。会话负责把同一段工作的多次执行关联起来；对话历史保存用户要求、模型回复和工具结果，下一次继续时加载进去；笔记单独保存需要长期记住的事实和结论，比如已经确认的约束。

这样既能知道前面具体做过什么，也能单独保留关键结论。历史会不断增长，笔记可以减少后续反复查找重要信息的成本。当前笔记由 Agent 主动保存，加载历史时也会截断过长的工具结果，避免单条输出占用太多上下文。

## 问：任务执行时间很长，上下文放不下了怎么办？

我主要用了两种方式：先减少过长工具结果的占用，再把较长的历史整理成摘要。项目支持手动压缩，也支持开启后根据上下文占用情况触发自动压缩，让后续执行从摘要接着做。

摘要会明确要求保留原始目标、已经完成的步骤、关键决策和约束、当前文件状态，以及剩下要做的事情。这样压缩的重点是保留继续任务所需的信息。摘要生成失败或返回空内容时，会保留原来的历史。

不过摘要仍然依赖模型，不能保证完全不丢信息。当前主要靠明确的摘要要求来降低遗漏风险，后续可以把关键任务状态单独保存，并检查摘要是否覆盖了这些内容。

# 五、子 Agent 协作与能力扩展

> CV：用 Skill 模板注入系统指令与工具白名单，把 MCP Tool 包装为统一工具基类，将子 Agent 的创建与结果回传注册进工具注册表；支持子 Agent 独立上下文、前台 / 后台执行、事件桥接与结果查询。

## 问：你怎么扩展 Agent 的能力？

我分成三种情况。常见任务需要固定的步骤和输出要求，就用 Skill 提供做法，并限定可用工具；需要连接外部工具，就通过 MCP 接入；需要把一块独立工作拆出去，就交给子 Agent。

比如代码审查可以通过 Skill 约定检查重点和输出格式，外部系统的能力可以通过 MCP 引入，单独分析一个模块则可以作为子任务。工具接入和子任务调用都复用统一的执行入口，这样权限控制、超时和结果反馈能沿用已有方案，核心任务流程不需要为每种扩展重新设计。

## 问：什么样的任务适合交给子 Agent？拆出去有什么代价？

我会优先拆目标清楚、依赖较少、能单独给出结果的任务，比如分析某个模块或者审查一组文件。主 Agent 交代目标、约束和必要背景，子 Agent 用自己的上下文执行，完成后再把结论交回来。小任务直接由主 Agent 做，避免额外的模型调用和协调成本。

独立上下文可以减少无关信息，但也意味着任务描述必须完整，否则子 Agent 容易缺少背景。另外，当前父子 Agent 共享本地文件，独立上下文并不等于文件隔离。涉及修改文件时，需要明确各自负责的范围，当前还没有自动解决文件冲突的能力。

## 问：主 Agent 怎么和子 Agent 配合，怎么拿到结果？

我主要看任务之间有没有依赖。如果下一步必须用到子任务的结果，就等待它完成，再把结果交回主 Agent；如果子任务可以独立推进，就放到后台，主 Agent 先做其他工作，之后通过查询获取子任务的状态和结果。

子任务的执行进度也会展示给用户，方便看到它在做什么。进度展示和结果回收是两件事：后台任务的最终结果还需要主 Agent 主动查询。这样可以支持独立任务同时推进，但任务怎么拆、什么时候查询，目前仍主要由模型决定，没有自动的依赖调度。
