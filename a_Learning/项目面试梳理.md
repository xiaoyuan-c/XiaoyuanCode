# 项目面试梳理

本文只围绕简历中的 XiaoCode 项目展开，目标不是解释全部源码，而是帮助我在面试中讲清楚：项目解决了什么问题、为什么这样设计、考虑过哪些替代方案、当前实现有哪些边界。

使用时建议先背每章末尾的“简洁背诵版”，再用“高频追问”补充细节。没有被问到时，不主动展开底层实现。

# 一 项目定位与整体架构

简历原文：

> 面向开发者的本地任务开发场景，构建可操作本地文件、命令行及外部工具的 Agent，帮助用户通过自然语言完成代码分析与书写、文件处理等工作，同时保证执行过程可控、可追踪。

## 背景阐述

这个项目不是普通的聊天机器人。普通聊天应用通常只需要把用户问题发给模型，再展示模型回复；但本地开发 Agent 需要真正读取文件、修改文件、执行命令，还要能够连续完成多个步骤。

一旦模型具备实际操作能力，系统就不能只关注“模型回答得好不好”，还要解决三个工程问题：

- Agent 如何连续决策和调用工具；
- 高风险操作如何被约束；
- 执行过程如何实时展示、持久化记录和后续复盘。

所以我把 XiaoCode 定位成一个本地 AI Agent Runtime，而不是一次性的 LLM 调用脚本。

## 问题剖析

整体进程架构常见有两种方案。

第一种是单进程：界面、Agent Loop、模型调用和工具执行全部放在一个进程中。它的优点是开发简单，但任务生命周期通常与界面绑定，界面退出容易连带中断任务；后续增加 CLI、TUI 或 Web 客户端时，核心逻辑也容易重复。

第二种是客户端与 runtime 分离的双进程：客户端只负责与用户交互，独立 daemon 负责会话、Agent Loop、工具、权限和持久化。它的实现成本更高，但任务生命周期与界面解耦，更适合多客户端和事件订阅。

本项目最终选择第二种方案。

## 方案构思

### 为什么使用 daemon 加多客户端

`kama-core` 是 runtime，CLI 和 TUI 是客户端。这样设计主要有三个原因：

- Agent 任务不依赖某一个界面的生命周期；
- CLI、TUI 可以复用同一套会话、工具和权限逻辑；
- 执行过程可以统一建模为事件，再由不同客户端按需订阅。

### 为什么客户端与 runtime 之间通信使用 TCP NDJSON 和 JSON-RPC 2.0

本地进程间通信（Inter-Process Communication，IPC）的底层通道可以选择 stdin/stdout 管道、Unix Domain Socket 或回环 TCP。stdin/stdout 更适合父子进程，较难支持多个独立客户端；本项目更适合使用 Socket。

如果在 Socket 之上封装 HTTP 服务，普通请求响应对短调用很友好；但 Agent 运行期间会持续产生 token、工具调用和审批事件，还需要使用 SSE、WebSocket 或流式响应处理持续推送。

Unix Domain Socket 更适合纯本机通信，但考虑到跨平台一致性、调试方式的通用性和后续扩展便利性，最终选择了回环 TCP（Loopback TCP）。

项目只监听 `127.0.0.1` 本机地址，并使用 NDJSON 划分消息边界：一行就是一个完整 JSON 消息，便于异步流式读取。

命令请求和响应使用 JSON-RPC 2.0。它提供请求 ID、方法名、方法参数、结果和结构化错误；其中请求 ID 为客户端在同一连接上关联多个在途请求与响应提供了基础，实际并发还依赖客户端和服务端的异步实现。服务端主动推送的事件使用自定义 `kind=event` 消息格式。两类消息都通过 NDJSON 传输。

命令、响应和事件模型通过 Pydantic 定义和校验，避免客户端与 daemon 之间依赖松散的字典约定。

### Agent 可控和可追踪分别怎么实现

“可控”主要由 Tool Runtime、权限策略、最大步数、超时和取消传播共同保证。“取消传播”是指异步任务收到取消后，`CancelledError` 沿调用链向上传递，各层先完成状态记录和清理，再继续抛给上层。

“可追踪”不是简单打印日志，而是把运行开始、每一步、模型 token、工具调用、权限审批和运行结束统一建模成事件。事件一方面推送给订阅它们的客户端，另一方面按每次 Agent 任务运行写入独立的 `events.jsonl`；系统还会按 IPC、EventBus（runtime 内部事件）和 LLM 三个层次记录 trace，分别用于检查客户端通信、内部执行过程和模型调用。

## 复盘总结

这个项目最核心的工程选择，是把“交互界面”和“Agent 执行内核”拆开。客户端负责输入和展示，daemon 统一管理会话、模型、工具、权限和事件。这种设计比单进程脚本复杂，但让任务生命周期、多客户端接入和执行追踪都有了稳定边界。

## 高频追问

### 这个项目和普通大模型套壳有什么区别

普通套壳通常是一问一答，模型只输出文本。XiaoCode 让模型通过 工具调用 操作文件、命令行和外部工具，并通过 ReAct 循环根据工具结果继续决策；同时加入权限、上下文、事件和持久化，所以重点是 Agent Runtime，而不只是模型 API。

### 为什么一定要拆 daemon，单进程不能做吗

单进程当然能做，而且原型阶段更简单。拆 daemon 的主要价值不是性能，而是生命周期和职责解耦：界面退出不等于任务立即退出，CLI 和 TUI 能共享同一套执行内核，后续也可以继续接其他客户端。

### 为什么不用 WebSocket

WebSocket 也可以，而且更适合未来接 Web 前端。当前项目是纯本地 Python 客户端，TCP 加 NDJSON 已经能满足双向长连接和事件推送，实现和调试成本更低。如果要跨网络部署，我会进一步考虑 WebSocket、鉴权和 TLS。

### Event 和普通日志有什么区别

日志主要面向排障，格式不一定稳定；
Event 是业务协议的一部分，有明确字段和数据类型，界面、持久化和回放都依赖它。比如权限审批不能只打一行日志，它必须成为客户端能够识别的结构化事件。

## 简洁背诵版

XiaoCode 是一个面向本地开发任务的 AI Agent Runtime，不是简单的一问一答应用。我把系统拆成常驻的 runtime 守护进程和 CLI、TUI 客户端，双方通过回环 TCP 和 NDJSON 通信，命令与响应采用 JSON-RPC 2.0，事件使用独立推送格式。runtime 统一负责 Loop、工具调用、权限、会话和上下文，执行过程通过结构化事件实时推送并持久化。这样设计主要是为了把客户端界面和任务生命周期解耦，同时保证执行可控、可追踪。

# 二 ReAct Agent Loop

简历原文：

> 实现「推理—行动—观察」执行闭环，解析模型文本、Tool Use 和任务终止状态，支持连续多轮工具调用，并通过最大步数、异常中断和取消信号避免 Agent 循环失控。

## 背景阐述

任务通常无法通过一次模型调用完成。例如模型要先查看目录，再读取文件，之后才能判断是否修改代码，最后还可能需要运行测试。前一步工具结果会影响后一步决策，因此需要一个持续运行的 Agent Loop。

## 问题剖析

这里常见有一些实现思路。

- 先生成完整计划再一次性执行：结构清晰，但计划无法及时吸收执行中的新信息。
- ReAct 循环：每次让模型根据当前上下文决定下一步，执行工具后再把结果交还模型。

本项目选择 ReAct，是因为代码分析和文件处理的路径通常不能预先完全确定，需要让模型根据观察结果动态调整。

## 方案构思

### Loop 中保存什么状态

我没有把循环状态散落在各个函数里，而是放在统一的执行上下文中，包括：

- 当前 run ID 和用户目标；
- messages 历史；
- 当前 step 和最大步数；
- running、success、failed 状态；
- 最终结果和失败原因；
- Session Notes、全局上下文 和项目上下文。

一次 run 的结构示例如下：

```text
run_id = run_001
├── step 1：调用模型 → 决定读取文件 → 执行工具 → 回填结果
├── step 2：调用模型 → 根据文件内容执行命令 → 回填结果
├── step 3：调用模型 → 决定修改代码 → 回填结果
└── step 4：调用模型 → 给出最终回答，不调用工具
```

一个 `step` 是 Agent Loop 的一次迭代：包含一次 Agent 决策所需的 LLM 调用，以及随后可能发生的 0～N 次工具调用。工具结果在当前 step 写入上下文，并在下一 step 被模型读取。

这样 Agent Loop 只负责状态推进，模型 Provider 和工具层保持相对独立。

### 一轮决策如何闭环

每一轮先把消息历史和当前可用工具的 Schema 列表发给模型。模型响应可能包含文本、thinking block 和零个或多个 `tool_use`。

`thinking block` 是部分模型返回的结构化思考块。如果模型返回了它，项目会保留其内容和签名，以满足后续工具调用续接时的消息格式要求；没有返回时不需要额外添加。

系统会先将模型本轮返回的内容（可能包括文本、thinking block 和工具调用请求）作为一条 assistant 消息写入上下文。如果模型请求调用工具，再依次执行相应工具；每个执行结果会被封装成 `tool_result`，作为 user message 回填，供下一轮模型调用参考。

如果模型返回 `end_turn`，当前文本成为最终结果；如果仍然返回 `tool_use`，循环继续；如果达到最大步数，则以 `exceeded_max_steps` 结束。

### 为什么要按顺序执行多个工具，而不是并发执行

多个工具调用如果互不依赖，可以并发执行。但模型一次返回的多个调用未必满足这个条件，例如对同一文件的写操作可能存在顺序要求。当前实现没有自动识别依赖关系，因此统一顺序执行，以简化副作用和权限审批的管理。

后续如果增加并发，我会要求模型显式声明依赖，或者只并发执行被标记为只读且互不依赖的工具。

### 如何控制任务终止与退出

项目用了多层终止条件：

- 模型正常返回 `end_turn`；
- 设置最大步数；
- LLM 异常时标记为 `llm_error`；
- 收到 取消信号 时先收敛状态，再向上传播；
- 守护进程关闭时，会主动取消尚未完成的后台单次任务，并等待任务完成取消处理后再退出。

最大步数是最后保险，不能替代清晰的 system prompt 和可靠的工具结果。

## 复盘总结

ReAct Loop 的价值不是“多调用几次模型”，而是建立一个受控状态机：模型负责选择行动，工具层负责执行，结果重新进入上下文，终止条件由运行时统一判断。这样开放任务有了动态调整能力，同时不会完全失去边界。

## 高频追问

### ReAct 中的推理是自己实现的吗

不是自己实现推理算法。这里的“推理”是模型基于上下文选择下一步动作。runtime 负责解析模型返回的结果，保存文本、思考内容 和 tool use，并驱动后续行动。

### 工具执行失败后为什么不直接结束

因为工具失败本身也是一种观察。系统会把错误信息和 `is_error` 标记封装成 `tool_result` 回填给模型，模型可以修改参数、选择其他工具或向用户说明无法完成。

### 为什么需要最大步数

模型可能反复调用同一个失败工具，或者在没有进展时继续尝试。最大步数可以防止陷入死循环，是熔断边界。它解决的是最坏情况，不代表步数越小越好。

### 输出达到 `max_tokens` 时怎么处理

如果 LLM 在某次输出时达到上限，可能留下不完整的 tool use。系统会为已解析到的工具调用补一个错误结果，维持 tool use 和 tool result 的消息配对，并提示模型下一轮拆小任务，而不是直接执行可能不完整的参数。

这个问题暂时不背
### 是否支持用户主动取消当前任务

当前还没有给用户提供取消当前任务的按钮或快捷键，也没有对应的客户端取消命令。底层 Loop 已能响应 `asyncio` 取消：任务收到取消后会停止后续执行、记录 `cancelled` 状态并向上传播；daemon 关闭时也会取消它维护的后台单次任务。后续可以在 TUI 中提供“停止当前任务”的操作，由客户端在内部携带当前 `run_id` 请求 Core 定位并取消对应任务，用户不需要直接接触 `run_id`。

## 简洁背诵版

我在项目里实现了一个受控的 ReAct Agent Loop。每轮把当前消息和工具 Schema 发给模型，模型返回文本或 tool use；工具执行结果再以标准 tool result 回填，模型据此继续决策。运行时统一维护 step、状态和消息历史，并通过 end turn、最大步数、LLM 异常和 asyncio 取消传播控制退出。当前多个工具按顺序执行，优先保证副作用和上下文顺序可解释。

# 三 Tool Runtime

简历原文：

> 基于 ToolRegistry 和 Pydantic Schema 统一工具注册、参数校验与调用分发，将 Tool Result 结构化回注模型上下文；区分 Schema、Runtime、Rate Limit 和 Timeout 异常并实施差异化重试。

## 背景阐述，为什么需要有 tool runtime 

Agent 能力扩展后，会出现文件读取、文件写入、Shell、任务管理、Subagent 和 MCP 等多种工具。如果每增加一个工具，就在 Agent Loop 中添加一段判断，核心循环会很快和具体工具耦合。

所以这里需要一个统一的 Tool Runtime，让 Agent Loop 只关心“模型要调用哪个工具、参数是什么、结果是什么”。

## 问题剖析

- 在 Loop 中使用大量 `if/elif`：直观，但扩展性差，Loop 会与具体工具耦合。
- 使用显式 Registry 管理工具：工具实现统一接口，再按名称集中注册。这种方式实现简单，足以支撑当前规模，也能统一查看工具清单和管理同名冲突。当前实现中，同名工具会被后注册的工具覆盖；更稳妥的做法是发现重复名称时直接报错，或者通过命名空间显式区分。

如果工具规模继续扩大，可以进一步采用配置驱动的自动注册，并根据任务动态筛选要提供给模型的工具 Schema，避免一次发送过多工具增加上下文开销和模型选择难度。

## 方案构思

### 如何统一不同工具

所有内建工具都实现统一 BaseTool 抽象，暴露：

- `name`：模型调用和 Registry 查找使用；
- `description`：使用场景描述；
- `input_schema`：给 LLM 看的工具调用的 JSON Schema，帮助生成正确的 tool_use；
- `params_model`：给 python 运行时用的 Pydantic 模型，真正执行类型校验；
- `invoke`：异步执行工具并返回 ToolResult。

ToolRegistry 维护“工具名到工具实例”的映射，同时将所有工具的 `input_schema` 汇总后交给模型。模型侧的 `input_schema` 和执行侧的 Pydantic `params_model` 都声明在同一个工具类上，但它们是两份独立定义，当前没有自动机制保证二者完全同步。

### 为什么要在执行前再次校验参数

JSON Schema 能引导模型生成正确参数，但模型输出不能被当成可信输入。真正执行前仍然要通过 Pydantic 检查必填字段、类型和取值范围。

如果校验失败，系统返回 `schema_error`，不会进入工具实现，更不会重试。因为同一份非法参数重复执行没有意义，应让模型根据错误重新生成参数。

### 为什么统一返回 ToolResult

一种方案是工具失败后直接抛异常，让整个 run 结束；另一种是将成功和失败都包装成结构化结果。

项目选择第二种。ToolResult 至少包含内容、是否失败和错误类型。这样工具层的失败可以成为模型的观察，Agent 有机会自我修正，同时界面也能统一展示工具成功或失败。

### 为什么实施差异化重试

不是所有错误都适合重试：

- `schema_error`：参数本身错误，不重试；
- `permission_denied`：用户已经拒绝，不重试；
- `timeout`：当前工具执行超时，避免重复启动长任务；
- `rate_limited`：遇到限流错误，立即重试可能又会被再次限流，使用指数退避等待；
- `runtime_error`：工具执行阶段产生的运行时错误当前也按暂时性故障处理，最多重试两次；工具不存在等执行前错误会直接失败。

重试采用指数退避，等待时间依次为 2 秒和 4 秒，总共最多尝试三次。这样比固定间隔更能避免服务尚未恢复时连续施压。

需要主动承认一个边界：`runtime_error` 范围比较宽，如果工具有非幂等副作用，盲目重试可能重复执行。更完善的设计应该为工具增加“是否幂等、是否可重试”的元数据，只对明确的瞬时错误自动重试。

## 复盘总结

Tool Runtime 的核心不是注册工具本身，而是把模型输出和真实执行之间建立一道稳定边界：统一 Schema、统一校验、统一权限入口、统一错误分类和统一结果回填。Agent Loop 因此不需要知道具体工具是文件工具还是远程 MCP 工具。

## 高频追问

### 新增一个工具需要改 Agent Loop 吗

不需要。新工具实现 BaseTool，声明名称、描述、Schema 和 invoke，再注册到 ToolRegistry 即可。Agent Loop 始终通过 Registry 查找和调用。

### 有 JSON Schema 为什么还需要 Pydantic

JSON Schema 主要是给模型看的生成约束，不是安全边界。Pydantic 是执行前的服务端校验，可以阻止缺字段、类型错误或越界参数真正进入工具。

### 工具结果为什么不直接返回字符串

字符串无法稳定表达成功、失败和错误类型。
ToolResult 让调用层知道是否成功，如果失败的话，能够根据失败类型决定是否重试、如何发布事件，以及回填模型时是否设置 `is_error`。

### 为什么 Rate Limit 要退避重试

限流通常是暂时状态，立即重试大概率继续失败。指数退避让重试间隔逐渐增大，可以降低对外部服务的持续压力，同时给服务恢复窗口。

### MCP 工具也使用 Pydantic 校验吗

当前不是。MCP 工具直接复用服务端发现得到的 `inputSchema`，没有对应的本地 Pydantic `params_model`。因此“Pydantic 统一校验”准确地说主要适用于内建工具；MCP 工具依赖外部 Schema 和 MCP 服务端校验。

### 如何避免工具重复执行

当前实现没有完整的幂等键机制。只读工具重复执行问题较小，但写入类工具不应该因为笼统的 runtime error 自动重试。生产化时我会在工具元数据中标记幂等性，并为远程写操作设计幂等键或结果确认机制。

## 简洁背诵版

我通过 BaseTool 和 ToolRegistry 统一管理工具，工具的名称、描述和 JSON Schema 会提供给模型，内建工具执行前再用 Pydantic 做参数校验。所有结果统一包装成 ToolResult，并以标准 tool result 回填上下文。错误处理上，我区分 Schema、权限、超时、限流和运行时错误，只对当前定义为暂时性的 Rate Limit 和 Runtime Error 做最多两次指数退避重试。这个设计让 Agent Loop 与具体工具解耦，不过生产化时还需要结合工具幂等性进一步收紧重试范围。

# 四 工具权限控制

简历原文：

> 在 Agent 执行工具前引入独立权限层，针对 Shell、文件写入等高风险行为实现命令规则匹配、工作目录越界检测、异步人工审批及单次/会话级/持久化授权策略。

## 背景阐述

本地 Agent 和聊天机器人最大的安全差异，是它能产生真实副作用。读取文件通常风险较低，但执行 Shell 或覆盖文件可能破坏项目，单靠 system prompt 告诉模型“谨慎操作”不能构成可靠安全边界。

因此权限判断必须放在模型之外，并且位于真正调用工具之前。

## 问题剖析

权限控制常见有几种方案。

- 全部放行：体验流畅，但高风险工具不可接受。
- 所有工具每次都询问：安全直观，但只读这种无风险操作也频繁打断用户。
- 只依赖静态黑白名单：效率高，但无法覆盖所有动态命令。
- 静态策略加运行时人工反馈：低风险操作自动处理，高风险或不确定操作询问用户。

本项目选择最后一种，在安全和交互成本之间做平衡。

## 方案构思

### 为什么权限层独立于工具

如果每个工具自己实现审批，策略会分散，新增工具时也容易遗漏。当前调用链在统一的 `invoke_tool` 中先做参数校验，再交给 PermissionManager 判断，批准后才执行工具。

这样权限层可以统一发布审批事件、等待客户端响应、处理超时，并记录允许或拒绝结果。

### 静态策略如何判断

当前默认策略大致是：

- `read_file`、`list_dir`、`note_save` 默认允许；
- `bash`、`write_file` 默认询问；
- 未明确登记的工具默认询问。

对于 Shell，策略层支持 deny pattern、allow pattern 和工作目录越界启发式检查。越界检查会识别绝对路径、`~`、`..`、`$HOME`、`$PWD` 和显式 `cd` 等形式。命中越界规则后强制进入人工审批，不能被普通 allow cache 绕过。

这里要准确表达：当前是正则和字符串层面的启发式检测，不是完整的 Shell AST 分析，也不是操作系统沙箱。

### 异步人工审批如何实现

如果决策是 ASK，PermissionManager 会按 `tool_use_id` 创建一个 Future，并发布 `permission.requested` 事件。当前由 TUI 展示工具和参数摘要，用户选择后再发送 `permission.respond`。

daemon 收到响应后找到对应 Future 并完成它，原来的工具协程才会继续。这种方式不会阻塞整个 asyncio 事件循环，同一连接仍然可以处理审批响应和其他命令。审批超时默认按拒绝处理。

### 授权结果如何复用

当前客户端支持四种选择：单次允许、始终允许、单次拒绝、始终拒绝。

始终允许或拒绝会写入内存缓存和 `~/.kama/policy.toml`，下次命中同一工具时可以自动决策；但 Shell 越界命令仍然强制询问。

源码虽然存在以 `(session_id, tool_name)` 为 key 的会话缓存，但当前“always”响应会同时写入会话缓存和持久化文件，协议没有单独暴露“仅本会话允许”的选项。因此简历中的“会话级”和“持久化”目前不能作为两个完全独立的用户策略来讲。

## 复盘总结

这套权限设计的关键是把模型意图和真实副作用隔开：模型可以提出工具调用，但最终能否执行由确定性的服务端策略和用户决定。静态规则降低频繁审批，Future 加事件流实现非阻塞人工确认，持久化策略减少重复操作。

当前实现仍然是教学型安全层，不能替代真正的进程沙箱、文件系统隔离和细粒度命令解析。

## 高频追问

### 为什么 system prompt 不能代替权限系统

Prompt 只能影响模型行为，不能保证模型一定遵守，而且还可能受到提示注入影响。权限系统位于工具执行路径上，是确定性的代码检查，即使模型提出危险操作，也必须通过策略或人工审批。

### 为什么低风险读取不每次询问

如果所有操作都询问，用户会产生审批疲劳，最后容易无脑允许。把读取和目录查看默认放行，把 Shell 和写文件交给审批，可以把用户注意力集中在真正有副作用的操作上。

### 为什么越界命令不能被 always allow 绕过

“始终允许某个工具”不应该等价于允许它访问任意系统路径。越界检查放在缓存之前，可以防止用户之前允许过普通 Bash 后，后续命令直接操作项目外文件。

### 正则检测 Shell 安全可靠吗

它只能覆盖常见模式，复杂引号、变量展开、子命令和符号链接都可能绕过。当前项目把它作为一道快速防线。生产化时应使用命令解析、真实路径规范化、子进程沙箱、最小权限账户，必要时使用容器或 OS 级隔离。

### 文件工具真的完全限制在当前目录吗

当前 `read_file` 和 `write_file` 会拒绝路径中的 `..`，但没有对 `resolve()` 后的绝对路径做完整 cwd containment 校验，绝对路径本身也没有在工具内部被拒绝。因此面试中不能说已经实现了严格的文件系统沙箱。

### 客户端断开后审批会一直挂起吗

PermissionManager 提供了按 session 取消待审批 Future 的能力，但当前 SocketServer 断开处理只移除事件订阅，没有把连接和 session 绑定后自动调用该能力。默认审批超时可以避免永久等待，但断连自动清理链路仍可继续完善。

## 简洁背诵版

我没有依赖 Prompt 约束危险操作，而是在统一工具调用入口前加入独立权限层。低风险读取默认允许，Shell、写文件和未知工具默认询问；Shell 还会做规则匹配和越界启发式检测。需要人工确认时，系统通过事件发布请求并挂起 Future，客户端响应后再恢复工具协程，超时默认拒绝。当前支持单次和 always 决策，always 会写入内存与 policy 文件；不过严格的会话级选项和 OS 级沙箱还没有完整实现。

# 五 Context Engineering

简历原文：

> 构建 Session、Thread、Notes 分层上下文，对超长 Tool Result 进行截断，并基于模型返回的上下文占用比例触发 LLM Compact；压缩时保留任务目标、关键决策、文件状态和剩余步骤，支持长任务连续执行。

## 背景阐述

Agent 的上下文增长速度比普通聊天更快，因为除了用户和模型文本，还会保存工具参数、文件内容、命令输出和错误信息。简单地无限拼接历史会增加费用和延迟，最终还会超过模型上下文窗口。

但直接删除旧消息也有风险：Agent 可能忘记原始目标、已经修改过哪些文件以及还剩什么任务。

## 问题剖析

长上下文常见有四种处理方式。

- 直接截断最早消息：实现简单，但容易丢失关键决策。
- 滑动窗口：适合普通聊天，但开发任务的重要信息不一定出现在最近几轮。
- RAG 检索历史：适合大规模长期记忆，但需要切分、索引和召回策略。
- LLM 摘要压缩：能把分散信息重组为任务交接摘要，但存在摘要遗漏和额外模型成本。

当前项目没有实现 RAG，而是采用“分层记忆、定向截断和 LLM Compact”的组合方案。

## 方案构思

### Session Thread Notes 分别解决什么问题

- Session 保存会话元数据、状态和关联 run，是多轮交互的生命周期边界。
- Thread 使用 JSONL 保存可直接回放给模型的 user、assistant 和 tool result 消息，是完整对话历史。
- Notes 保存 Agent 主动提炼的耐久事实，例如用户偏好、关键约束和重要结论，不需要每次从长历史中重新推断。

此外系统还会加载用户级 `~/.kama/context.md` 和项目级 `.kama/context.md`，把稳定规则注入 system prompt。

这种分层的核心不是文件数量，而是区分“原始过程”和“需要长期保留的结论”。

### 为什么优先截断 Tool Result

工具输出往往是上下文中体积最大、信息密度最低的部分，例如完整日志或大文件。相比直接删除用户目标和模型决策，保留工具输出前缀并标注省略字符数，对任务语义的破坏更小。

当前默认超过 8000 字符时保留前 4000 字符，并提示完整结果可以从 run events 中查看。

### Compact 为什么交给 LLM

机械截断不知道哪些内容对后续任务重要。LLM Compact 会要求模型按固定结构生成交接摘要，重点保留：

- 原始目标；
- 已完成步骤；
- 关键约束和发现；
- 当前文件状态；
- 剩余任务；
- 后续必须保留的关键数据。

压缩成功后，内存中的长消息会被替换成“摘要 user message + assistant 确认”两条消息，让后续模型从摘要继续。

### 为什么根据上下文占用比例触发

固定按消息条数触发并不准确，因为一条命令输出可能比几十条短消息更长。Provider 会根据模型返回的 input tokens 和已知 context window 计算占用比例，Agent 在一次工具观察结束、准备继续下一轮时判断是否压缩。

项目同时提供手动 `/compact`，因为用户可能希望在阶段切换时主动整理上下文。自动压缩阈值默认是 0，也就是默认关闭，需要显式配置后才会触发。

### 如何降低摘要丢失风险

当前方案通过结构化 Prompt 强制覆盖目标、决策、文件和 TODO，并把摘要写入文件。手动压缩会先备份旧 Thread，再用压缩后的消息替换。

但摘要仍然可能遗漏细节，所以可追踪的 events、原 Thread 备份和 Notes 很重要。更进一步可以在摘要后做事实校验，或者把关键文件状态通过工具重新读取，而不是完全相信摘要。

## 复盘总结

Context Engineering 的目标不是单纯减少 token，而是在有限窗口中保留对后续决策最有价值的信息。项目用 Thread 保存过程、Notes 保存耐久事实、Context 文件保存稳定规则，再通过 Tool Result 截断和结构化 Compact 控制体积。

## 高频追问

### Notes 和 Thread 有什么区别

Thread 是按顺序保存的完整交互过程，内容多且增长快；Notes 是 Agent 主动提炼的长期事实，内容少但重要。二者分别对应过程记忆和耐久记忆。

### 为什么不直接保留最近 N 轮

开发任务中的关键约束可能出现在很早的位置，只保留最近 N 轮可能把原始目标或重要设计决定删掉。结构化摘要能跨越时间位置提取对后续有用的信息。

### 如何知道 Context 快满了

模型响应会返回 input token usage，Provider 再除以代码中记录的模型 context window，得到 `context_pct`。相比按字符数或消息数估计，这更接近模型实际看到的上下文占用。

当前 context window 映射只明确登记了少数 Claude 模型，未知模型统一按 200K 估算。因此接入 DeepSeek 等兼容接口时，如果实际窗口不是 200K，`context_pct` 会有偏差，生产化时应把模型窗口配置化。

### Compact 会不会导致幻觉或信息丢失

会有这个风险，所以摘要 Prompt 固定要求覆盖目标、决策、文件状态和 TODO。手动 `/compact` 会备份原 Thread，系统还保留事件记录；后续涉及关键事实时，应重新读取实际文件验证，而不是只依赖摘要。

### Tool Result 截断后如何查看完整输出

回填模型的内容会保留前缀并标记省略量，完整工具输出已经记录在当前 run 的事件文件中，可以通过事件回放或 trace 排查。

### 当前 Tool Result 截断有哪些实现边界

当前截断发生在 SessionStore 重新读取历史时，也就是主要控制跨轮回放的体积；同一个 run 内刚产生的超长结果不会立即经过这段截断逻辑。另外配置对象虽然声明了截断阈值和保留长度，但实际调用仍使用固定默认值。面试时不要把它说成已经完全配置化、覆盖所有路径。

### 自动 Compact 的持久化是否完整

自动 Compact 会替换当前 ExecutionContext 中的消息，并把摘要写入独立文件，因此同一个 run 的后续 step 可以从摘要继续。但 Runner 最后仍按压缩前的历史长度截取新增消息，压缩后的消息可能无法正确写回 Session Thread。手动 `/compact` 会直接备份并重写 Thread，链路更完整。因此不能把自动压缩描述为已经可靠覆盖跨 run 续接。

## 简洁背诵版

我把上下文拆成 Session、Thread 和 Notes：Session 管生命周期，Thread 保存完整消息，Notes 保存需要长期保留的关键事实，同时还支持用户级和项目级 Context。跨轮重新加载 Thread 时，系统会优先截断超长 Tool Result；当模型返回的 context 占用比例达到配置阈值后，再用 LLM 生成结构化交接摘要，保留目标、决策、文件状态和剩余任务。相比简单滑动窗口，这种方案更适合长开发任务，但摘要仍需通过文件和事件证据校验。

# 六 Agent 扩展与协作

简历原文：

> 基于 Skill 模板注入系统指令与工具白名单，将 MCP Tool 包装为 BaseTool，并将 spawn_agent/agent_result 注册到 ToolRegistry；支持子 Agent 独立上下文、前台/后台执行、事件桥接和结果查询。

## 背景阐述

基础 Agent Loop 能完成通用任务，但继续扩展时会遇到三类需求：

- 同一种任务希望复用稳定工作方法；
- 外部系统的工具希望低成本接入；
- 复杂任务希望拆给独立角色，避免主上下文持续膨胀。

这三类需求分别对应 Skills、MCP 和 Subagent。

## 问题剖析

一种做法是把所有能力都写进主 Agent 的 system prompt 和代码分支，但结果会是 Prompt 越来越长、工具接入方式不统一、复杂任务全部挤在一个上下文里。

项目没有重新设计三套执行引擎，而是尽量把扩展能力收敛到已有边界：Skill 负责改变指令和工具范围，MCP Tool 与 Subagent Tool 都进入 ToolRegistry，最终仍然由同一个 Agent Loop 调用。

## 方案构思

### Skill 为什么采用模板加工具白名单

Skill 可以选择只拼接一段普通 Prompt，也可以直接写死一套代码工作流。

只拼 Prompt 很轻，但无法限制当前任务可使用的工具；写死工作流可控，但复用和调整成本高。当前 Skill 使用 Markdown 模板保存角色指令和任务方法，同时可以通过 `allowed_tools` 声明工具白名单。

用户输入 `/skill-name arguments` 时，系统解析 Skill，用模板覆盖当前 run 的 system prompt，并在构造 ToolRegistry 时按白名单过滤工具。SkillLoader 虽然实现了 `$ARGUMENTS` 替换，但当前 Session 调用链把未替换的原始模板作为 system prompt，同时历史消息又优先于渲染后的 goal，因此替换结果没有真正进入模型上下文。模型仍能从原始 `/skill-name arguments` 用户消息看到参数，但不能说 `$ARGUMENTS` 注入已经完整生效。

这种方案的价值是把“怎么完成一类任务”从通用 Prompt 中拆出来，同时用最小工具集降低误操作概率。Skill 查找顺序是项目本地、用户全局、内建，便于项目覆盖通用配置。

### MCP 为什么包装成 BaseTool

接外部工具可以为每个服务单独写 HTTP 适配器，但每接一个服务都要处理不同协议。MCP 提供统一的初始化、工具发现和工具调用规范，适合作为外部工具接入层。

daemon 启动时按配置连接 stdio 或 TCP MCP Server，执行初始化和 `tools/list`。发现到的工具会包装成 BaseTool，并使用 `server_name__tool_name` 作为名称，避免多个 Server 出现同名工具。

包装后 Agent Loop 不需要区分内建工具和 MCP 工具，权限、事件和结果回填仍然走统一调用路径。

### Subagent 为什么也设计成工具

如果在 Agent Loop 内硬编码多 Agent 调度，会让主循环承担角色编排、并发和结果聚合。项目把 `spawn_agent` 和 `agent_result` 注册成普通工具，让主 Agent 根据任务自行决定是否派生子 Agent。

子 Agent 使用新的 ExecutionContext，只接收显式传入的 prompt，不继承父会话历史。这样可以减少无关上下文，也要求父 Agent 在派发时把目标、约束和期望输出说完整。

子 Agent 可以加载 planner、executor、reviewer 等角色配置，角色主要控制 system prompt 和工具白名单。它与父 Agent 共享模型 Provider、权限管理器和本地文件系统，因此“上下文隔离”不等于“资源完全隔离”。

### 前台和后台模式如何选择

前台模式会等待子 Agent 完成并直接返回结果，适合后续步骤立即依赖该结果的任务。

后台模式会通过 `asyncio.create_task` 启动子 Agent，并立即返回 run ID。主 Agent 稍后调用 `agent_result` 查询状态或取得结果，适合多个相互独立的子任务并行执行。

需要区分：当前主 Loop 中同一轮的普通工具调用仍然是顺序执行；并发能力来自后台 Subagent，而不是所有 Tool Calling 自动并行。

### 为什么需要事件桥接

子 Agent 有自己的 EventBus 和 run ID。如果这些事件只留在子总线，TUI 只能看到父 Agent 在等待，用户无法判断子任务进展。

所以子 EventBus 的事件会桥接到父 EventBus，并额外发布 `subagent.started` 和 `subagent.finished`。这样前端可以按 child run ID 展示嵌套进度，每个子 run 也有独立事件文件。

## 复盘总结

Skills、MCP 和 Subagent 解决的是三个不同问题：Skill 复用方法，MCP 接入外部能力，Subagent 隔离复杂子任务。实现上的共同点，是尽量复用 system prompt、ToolRegistry、Agent Loop 和 EventBus 这些已有边界，避免为每种扩展重新写一套执行逻辑。

## 高频追问

### Skill 和 Subagent 有什么区别

Skill 仍然在当前 Agent 和当前 run 中执行，主要改变 system prompt 和可用工具；Subagent 会创建独立执行上下文和新的 run，更适合上下文较长、角色明确或可以并行的子任务。

### MCP 和普通 Tool Calling 有什么区别

Tool Calling 是模型表达“我要调用哪个工具”的机制；MCP 是应用与外部工具服务之间的标准接入协议。MCP 工具最终仍然要作为 Tool Calling Schema 提供给模型，两者位于不同层次。

### 子 Agent 是否继承父上下文

不继承。它只接收父 Agent 显式传入的 prompt，这可以减少上下文污染，但也带来信息遗漏风险。因此派发子任务时必须包含完整目标、约束、相关路径和期望输出。

### 后台 Subagent 怎么拿结果

`spawn_agent` 在后台模式下立即返回 child run ID，并把 asyncio Task 和 ExecutionContext 存入运行时注册表。主 Agent 随后使用 `agent_result` 查询；未完成时返回 `still running`，完成后返回最终文本。

### 如何防止无限派生子 Agent

当前实现限制嵌套深度，达到两层后拒绝继续派生；每个子 Agent 自身也受最大 step 限制。生产化时还可以增加并发数、总 token、总费用和总运行时间预算。

### 不同 Subagent 会使用不同模型吗

角色配置中虽然存在 model 字段，但当前 SpawnAgentTool 仍然复用父 Agent 传入的 Provider，没有根据角色真正切换模型。因此现在主要实现的是角色 Prompt 和工具权限差异，不能说已经实现了完整的多模型路由。

### 当前 MCP 支持到什么范围

当前实现支持 stdio 和 TCP 连接、初始化握手、工具发现和工具调用，并把文本结果返回 Agent。它还没有覆盖 MCP Resources、Prompts、复杂内容类型、自动重连和完整的连接健康管理，所以应表述为 MCP Tool 接入，而不是完整 MCP 平台。

### 后台结果能跨用户消息查询吗

当前后台任务注册表属于一次 AgentRunner 实例，主要支持同一个父 run 在后续 step 中查询。SessionManager 每次处理新消息会创建新的 Runner，因此不能把它描述为跨 run 持久化的任务中心。

## 简洁背诵版

我把 Agent 扩展分成三层。Skill 用 Markdown 模板注入任务方法并通过工具白名单限制能力范围，适合复用稳定工作流；MCP Server 在 daemon 启动时完成工具发现，MCP Tool 再包装成 BaseTool 进入统一 Registry；复杂任务则通过 `spawn_agent` 创建独立上下文，可以前台等待，也可以后台执行后用 `agent_result` 查询。子 Agent 事件会桥接到父 EventBus，因此 TUI 能展示嵌套进度。三种扩展最终都复用现有 Agent Loop。

# 八 项目整体背诵话术

## 三十秒版本

XiaoCode 是我实现的一个本地 AI Agent Runtime，主要面向代码分析、文件处理和多步骤开发任务。它不是简单调用一次模型，而是通过 ReAct Loop 让模型持续进行工具调用和结果观察。我重点实现了统一 Tool Runtime、工具权限、分层上下文与 LLM Compact，并通过 Skills、MCP 和 Subagent 扩展能力。系统采用 daemon 加 CLI、TUI 客户端的结构，执行过程通过事件流实时展示并持久化，核心目标是让 Agent 既能执行真实操作，又保持可控和可追踪。

## 一分钟版本

XiaoCode 是一个面向本地开发任务的 AI Agent Runtime。整体上我把 TUI、CLI 和核心执行进程拆开，客户端通过回环 TCP 和 NDJSON 与 `kama-core` 通信，其中命令与响应采用 JSON-RPC 2.0，daemon 负责会话、模型、工具和权限。

执行层的核心是 ReAct Agent Loop：模型每轮根据消息历史决定是继续输出还是调用工具，工具结果会以标准 Tool Result 回填上下文，直到模型结束或达到最大步数。工具层通过 ToolRegistry 和统一 BaseTool 接口解耦具体实现，内建工具使用 Pydantic 校验参数，调用层再根据错误类型决定是否重试。

因为 Agent 可以执行 Shell 和写文件，我把权限判断放在模型之外，通过静态策略、越界启发式检测和异步人工审批控制副作用。长任务方面，我用 Session、Thread 和 Notes 区分生命周期、完整过程和耐久事实，并通过跨轮回放时的 Tool Result 截断与结构化 LLM Compact 控制上下文增长。

扩展上，Skill 负责复用指令和工具白名单，MCP Tool 包装后进入统一 Registry，复杂任务可以派生独立上下文的 Subagent，并支持后台执行和结果查询。整个过程会产生结构化事件，用于 TUI 展示、事件回放和系统 trace。

## 面试时的表达原则

- 先说业务问题，再说技术选择，不要一上来背类名。
- 每个设计至少准备一个替代方案和没有选择它的原因。
- 主动区分“已经实现”“底层支持”“后续可完善”。
- 权限和重试问题不要只讲优点，要能说出正则检测、幂等性和沙箱边界。
- 被问到源码时，再落到 AgentLoop、ToolRegistry、PermissionManager、SessionStore 等模块。
- 不把 EvoEval、RAG、Redis 或数据库能力混入 XiaoCode，这些不属于该项目当前实现。
